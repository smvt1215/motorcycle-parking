## 0. 決策紀錄（2026-10-25）

1. 加入遊戲化機制，目標 95% 的審查由社群完成。
2. 官方點的資料修改採 §5.6 的覆蓋層模式。
3. **開放原則：不涉及法規修改及資料穩定性的點位資訊，原則上開放給社群結案，依風險等級作業。** 據此把所有欄位與案件分成三類（§5.1）：

| 類別 | 定義 | 誰結案 |
| --- | --- | --- |
| A 法規類 | 縣市規則、路邊格位的合法性判斷（指由縣市規則推導的車種資格結論，不含格位存在、型式、收費等事實欄位）、官方明載停放資格的改變、官方點的來源與授權 | 管理員（禁區，社群不產生任務）；由法規預審引擎（§5.7）先以現行規則自動回答或整理成附引用的案件 |
| B 資料穩定性類 | 改變點位身分或會讓其他資料失效的操作：隱藏／刪除、型式跨路外／路邊變更、位置移動 > 150 m、合併或拆分重複點、改為官方點、官方 `effective_date` | 管理員結案；社群依風險等級**預審**（達共識即成為「已預審」案件，管理員只需確認），不直接生效 |
| C 開放類 | 其餘點位資訊：名稱、入口、指引、備註、照片、分區、費率、同類內型式、場站型式、位置 ≤ 150 m、點位存在、路外場站業者的車種規則 | 社群依低／中／高風險結案 |

B 類保留管理員結案的理由不是不信任社群，而是這些操作一旦錯誤會連帶使其他核實失效或讓點位消失，回退成本高；社群預審讓管理員的工作從「審」變成「確認」。

4. 所有提案在分類之前先經過兩道自動檢查：**預檢模組**（§5.8，欄位矛盾、違規內容、行為異常）與**法規預審引擎**（§5.7，用現行規則回答或整理 A 類提案）。兩者都不判斷對錯、不改點位資料與資格判斷，只決定提案能不能進、進哪裡、帶什麼旗標；引擎寫入的只有規則佐證紀錄與案件。
5. 社群結案率的分母排除 A／B 類案件，A／B 類量另列（§2.1、§2.2）。
6. B 類「已不存在」的社群預審採中風險門檻（3 票含 1 名 L2＋、0 票不同意，不需 L3 照片）；其他 B 類維持高風險門檻。中間狀態 `reported_gone` 本身安全，隱藏仍由管理員確認。
7. 預檢 `hold` 的提案仍由社群結案，共識門檻加 1 票且 L0／L1 提交的照片不計入門檻。
8. 點數第一年不開放兌換金錢或實物；只做等級、徽章、排行榜、任務。
9. 官方點的「明載」旗標 `vehicle_source` **先回填再開放**：匯入工具補上旗標並完成既有 1,497 筆回填之前，官方點的車種欄位不開放社群核實，只能標爭議。
10. 預檢硬拒絕（`reject`）只限個資、官方來源欄位（`validate.ts` 已擋，預檢補記錄）、政策禁止項；其餘矛盾一律 `fix`，修正後可重送。
11. 核實計畫的修訂（§1 不在範圍句、§2.2 與 §3.3 費率策略）現在另開 PR 一起改（#87 已合併）；階段 0 的實作在本研究文件合併後另開 session，分成小 PR。
12. **駁回分類定為 6 類**：`wrong`（與現況不符）、`duplicate`（與既有案件或已處理的建議重複）、`insufficient`（資訊不足、無法查證）、`outdated`（點位已更新，建議不再適用）、`abuse`（濫用）、`other`（其他，需寫處理說明）。在 §6 原本 4 類之外加上 `insufficient` 與 `outdated`，是為了讓 §5.3 計分時只有 `wrong`、`abuse` 算提案者的錯，不會因為無法查證或資料已更新就誤罰。`resolution_note` 只給管理員看，回報者只會看到依分類顯示的固定文案。

## 1. 結論

**95% 社群審查是可以達成的目標，但前提是三件事同時成立：社群要能「結案」而不只是「提供觀察」、遊戲化只獎勵「事後證明正確」的貢獻、管理員的 5% 要定義成「爭議、申訴、法規與隨機抽查」而不是「剩下沒人審的」。**

- **今天 0% 由社群結案。** `moderation_queue` 只能由 `admin_resolve_report`（`is_admin()`）結案；社群只能送出結構化修改建議（`flag`）與舊 `vote`。要到 95%，核心不是獎勵，而是先給社群一條能結案的路徑：審核任務、共識規則、依風險分級決定誰能結案（§5）。
- **遊戲化可以納入，但要綁在結果上。** 點數只在「採納、共識成立、照片被確認」時發放，在「被翻案」時扣回並加罰；等級同時看點數與準確率，刷量不會升級（§5.3、§5.4）。這與核實計畫原則 2「社群提供觀察與證據，不以多數票取代法規」並不衝突：法規與路邊格位合法性仍是管理員禁區，社群結案的是事實類欄位與路外場站業者規則（#85 §5.2 例外）。
- **信任等級是遊戲化的骨架。** 系統已有沒有名字的兩層（帳齡 7 天決定 `qualified` 與權重 0.25／1）與管理員布林角色（§3）。本文擴成 L0–L4 五級加管理員，L3 以上自動取得 #85 要求的「經授權的審核角色」能力（照片內容確認），不再只靠管理員人工授予（§5.2）。
- **95% 要用指標驗收，不是宣告。** §2 定義「社群結案率」與護欄指標「翻案率」；每個欄位類別只有在翻案率低於門檻時才開放社群自動結案，否則退回管理員。管理員的 5% 中固定包含隨機抽查，這是量測翻案率的來源。
- **誠實的限制。** 95% 是吞吐量目標，取決於活躍審核者人數。冷啟動期達不到，建議分段 50% → 80% → 95%（§9）。每月約需「案件數 × 3」次審核動作，少於這個量就會回落到管理員（§2.3）。
- **官方點採「覆蓋層」核實模式（§5.6）。** 官方點占目前匯入資料的七成（1,497 官方對 630 社群），不能整批列為禁區。決定：官方值本身永遠不被社群改寫，社群核實的結果存成獨立的覆蓋層並與官方值並列顯示；官方值變動時覆蓋層自動失效；只有「來源、生效日、隱藏、官方明載的停放資格」四類維持管理員。這同時修正一個既有問題：重新匯入會覆寫 `official_heavy_spots` 除隱藏與生效日外的全部欄位，今天管理員採納的修改在下次匯入就會消失。
- **仍然不建議的部分。** 可兌換金錢或實物的點數：涉及稅務、消費者保護與更強的刷分誘因，第一年只做非金錢的等級、徽章、排行榜與任務（§0 第 8 點已決定）。

## 2. 目標定義與量測

### 2.1 指標

| 指標 | 定義 | 目標 |
| --- | --- | --- |
| **社群結案率** | 當月結案的審核案件中，由社群機制（共識自動結案、L4 駁回／維持）結案的比例。分母排除「政策規定只能由管理員處理」的類別（§5.1 禁區）；抽查是對已結案案件的複核，不是結案，不在分子也不在分母 | 分段：上線 3 個月低風險類別 ≥ 50%、6 個月全部類別 ≥ 80%、12 個月 ≥ 95% |
| **管理員逐案結案率** | 當月由管理員逐案結案的非禁區案件（爭議終審、申訴、逾時回流）占非禁區結案的比例；就是 1 − 社群結案率 | 穩態 ≤ 5% |
| 管理員工作量 | 管理員逐案結案＋A／B 類案件＋抽查件數＋角色與閘門管理的時數 | 監看用，不設目標；抽查工作量≈社群結案數 × 抽查比例 |
| **B 類預審率** | B 類（資料穩定性）案件中，管理員結案時已有社群共識預審的比例 | ≥ 80%；管理員對已預審案件的否決率另列，過高表示預審規則要調整 |
| **A 類引擎一致率** | 涉及法規結論的提案中，被法規預審引擎（§5.7）判為與現行規則一致、不進管理員佇列的比例；「缺規則」另列為缺規則率，不算回答 | 一致率 ≥ 50%；另列規則複查任務數與其中導致規則更新的比例 |
| **預檢誤攔率**（護欄） | 被預檢模組（§5.8）`fix`／`reject` 的提案中，經申訴或管理員覆核認定無誤的比例；攔截率另列 | ≤ 5%；單一規則 30 天內觸發 ≥ 50 次且誤攔 > 20% 即自動停用並通知管理員；樣本不足只監看 |
| **翻案率**（護欄） | 以「結案後 90 天」為觀察窗，對每個滾動 90 天的結案批次計算被管理員或後續證據推翻的比例，依欄位類別分開算；批次樣本 < 100 件時只監看、不觸發閘門 | 低風險 ≤ 3%、中風險 ≤ 5%；超過即該類別暫停自動結案。指標有 3 個月遲滯，階段驗收需等第一個完整批次 |
| **抽查不合格率**（護欄） | 管理員隨機抽查社群結案案件的不合格比例；樣本 < 100 件時只監看 | 與翻案率同門檻；抽查比例起始 5%，翻案率穩定後可降到 2%；案件量少時以「每月至少 30 件」取代比例 |
| 審核時效 | 案件從送出到結案的中位數天數 | 社群 ≤ 7 天（參考值，依資料調整） |
| 審核者覆蓋 | 近 30 天完成至少 1 件審核任務的 L1＋人數、每縣市分布 | 監看用，決定是否有足夠人力開放某縣市 |

### 2.2 為什麼分母要排除禁區

A 類（法規）與 B 類（資料穩定性）依 §0 第 3 點只能由管理員結案；核實計畫 §1 原則 2 與 §3.3 對 A 類另有明文要求。這些案件無論社群多活躍都不能由社群結案；把它們放進分母，95% 會變成做不到的數字，反而誘使放寬邊界。正確做法是**讓 A／B 類案件量本身很小、且 B 類盡量已預審**：法規由管理員維護 `city_rules` 而非逐案審；官方點的修改建議依 §5.6 以覆蓋層由社群核實；B 類由社群預審後管理員只做確認（§2.1 的預審率）；申訴只在翻案時發生。官方點占目前匯入資料的七成，若把官方點修改全部列為禁區，禁區案件量會大到讓「95%」失去意義，這是 §5.6 存在的原因。

### 2.3 人力試算

每件案件依 §5.1 需要 2–3 名獨立審核者；加上升級為爭議的重審，粗估每件 3 次社群審核動作。管理員抽查另計（§2.1 的工作量列）。

```text
每月所需審核動作 ≈ 當月案件數 × 3
每月所需活躍審核者 ≈ 審核動作 ÷ 每人每月願意做的件數（保守 5 件）
例：每月 200 件 → 600 次審核 → 約 120 名活躍 L1＋，且要分布在案件所在縣市
```

活躍審核者少於這個量時，案件會逾時（§5.1 的 14 天）回到管理員，社群結案率自然下降。這就是為什麼遊戲化要存在：它的工作是把「願意做 5 件」的人數養起來，而不是讓每個人做更多件。

### 2.4 量測基線（階段 0）

導入遊戲化之前先記錄基線，之後才能比較社群結案率與時效。`admin_review_baseline(p_months int default 12)`（security invoker，先檢查 `is_admin()`，非管理員或沒有 `aal2` 一律 `42501`）以 Asia/Taipei 月份分組，每月一列、最新的在前：

| 欄位 | 定義 |
| --- | --- |
| `reports` | 當月入列的案件數 |
| `reporters` | 當月案件中不重複的回報者人數（投票觸發的案件沒有回報者） |
| `auto_reports` | 當月由投票觸發、沒有回報者的案件數 |
| `resolved` | 當月結案數，不論結案方式（含 Dashboard 舊路徑） |
| `admin_resolved` | 當月經 `admin_resolve_report` 結案的件數（`resolved_by` 有值） |
| `median_hours` | `admin_resolved` 從入列到結案的時數中位數 |
| `by_status` | 當月結案依 `accepted`／`rejected`／`closed` 分布 |
| `by_resolution_kind` | 當月結案依分類分布；`unclassified` 是沒有記錄分類的件數 |
| `by_risk` | 當月入列依風險分布；`unclassified` 是沒有推導出風險的件數 |

限制：「結案不修改」在資料表上同樣是 `accepted`，要分開算得看稽核紀錄裡 `spot` 是否為 null；社群結案上線前，`admin_resolved` 就等於全部的逐案結案。目前只做資料層，不做儀表板（ADMIN_WEB.md「不在範圍內」）。管理員可在 SQL Editor 以 admin JWT 執行，或之後由指標頁讀取。

### 3.2 現在缺的

- **社群沒有結案路徑。** 只有 `admin_resolve_report` 能把案件從 `pending` 改掉。
- **使用者看不到自己的貢獻。** `moderation_queue` 只有 `admin_read_moderation` 一條讀取政策；貢獻頁（`lib/features/contribute/`）只列目前地圖範圍內的停車點。
- **駁回沒有分類。** `rejected` 只有自由文字 `resolution_note`，分不出「判斷錯誤」「重複」「濫用」。（階段 0 已補上 `resolution_kind` 與 `risk`，見 §6 與 [ADMIN_WEB.md P3](ADMIN_WEB.md#p3-實作)。）
- **沒有使用者資料表。** #83 把顯示名稱與頭像放在 `raw_user_meta_data`（使用者可自改）；#81 把名稱快照到 `community_spots.contributor_name`。等級、點數屬伺服器判定的資料，**不能放 `raw_user_meta_data`**。
- **沒有中間角色。** `is_admin()` 是布林；#84 的核驗 trigger 與所有管理 RPC 都以它為唯一閘門。

## 5. 達到 95% 需要的機制

### 5.1 社群審核流程與共識規則

**審核任務。** 每件待審案件（修改建議、新增停車點、已不存在回報、照片證據）成為一個任務，推給符合條件的審核者：不是提案者本人、與提案者不同 IP／裝置、等級達到該風險類別的門檻、近期在該縣市有活動（以目前地圖範圍查詢，不儲存位置歷史）。任務內容是「目前值／建議值／證據」加上三個選項：同意、不同意、無法判斷，並可附現場照片。

**依風險分級決定誰能結案。** 每票權重都是 1；等級決定「能不能投」與「結案需要哪種組合」。下表的低／中／高是 §0 第 3 點 C 類（開放類）的風險分級；B 類（資料穩定性）沿用同一套票數門檻做**預審**，但結案者是管理員；A 類（法規）不產生社群任務。

| 風險 | 欄位／案件 | 結案條件（自動） | 失敗時 |
| --- | --- | --- | --- |
| 低 | 名稱、入口說明、停車指引、備註、照片是否可公開、點位存在（沿用現行兩名合格者） | 2 票同意（L1＋）、0 票不同意、提案送出後相關欄位未被改過（`moderation_queue.base_spot` 比對） | 任一不同意 → 升為中風險處理 |
| 中 | 費率（需現場收費牌照片；核實計畫 §3.3 需同步修訂）、同類內的格位型式變更（路邊格位之間）、場站型式 `facility_type`、位置移動 ≤ 150 m | 3 票同意、其中至少 1 名 L2＋、0 票不同意；`facility_type` 變更後該點社群車種核實失效（#84 trigger 同時清除管理員核驗），資格回到「待確認」 | 任一不同意 → 標 `disputed`，由 L4 初審；L4 只能駁回或維持，無法駁回時 → 管理員 |
| 高 | 路外場站業者的車種規則（#85 §5.2 例外） | 3 名獨立 L1＋同意＋1 張經 L3 確認內容的入口公告照片；型式與位置已由官方或管理員核實且無 B 類待決案件；無相反觀察；寫入 `source_kind='community'`，有效期 90 天 | 相反觀察 → `disputed` → 管理員 |
| B 類預審（管理員結案） | 「已不存在」（隱藏）、型式跨路外／路邊變更（`space_type` 進出 `offStreet`）、位置移動 > 150 m、合併重複點、改為官方點 | 「已不存在」以中風險門檻預審（3 票含 1 名 L2＋、0 票不同意，§0 第 6 點）；其餘 B 類以高風險門檻預審（3 票含 L2＋＋1 張 L3 確認的現場照片）→ 案件標「已預審」進管理員佇列，管理員一鍵確認或否決。預審達成時先套用安全的中間狀態：「已不存在」標 `existence='reported_gone'`（降為待確認、搜尋排序後移、地圖維持顯示）；型式跨類與大幅移位先讓該點所有車種核實失效、資格回「待確認」，欄位本身待管理員確認才改 | 否決 → 參與者依 §5.3 扣分；`hidden` 仍只由管理員寫入（#59、ADMIN_WEB.md「騎士不能單方面下架」） |
| A 類（禁區） | 縣市法規、路邊格位合法性、官方明載停放資格的改變、官方點的來源與授權、申訴終審、撤銷角色 | 只有管理員，不產生社群任務 | — |

官方點的修改建議不是整批禁區：依 §5.6，社群核實的結果存成覆蓋層，官方值本身不動；上表的分類同樣適用於覆蓋層。

- 等級高不會讓一票變兩票；L3 在高風險類別的角色是「確認照片」，不是「多一票」。
- 型式跨路外／路邊變更列為 B 類的原因：非路外的社群點依縣市規則推導資格，把私人場站改標成路邊收費格就能間接得到「可停」；#85 §9 只防「路邊改路外」，這裡補上反向。預審達成時先讓車種核實失效，是為了在管理員確認前就關掉這條繞道。
- 任務 14 天無人完成或票數不足 → 回到管理員佇列，並計入「管理員逐案結案」。
- 同一欄位出現矛盾的可靠觀察時，保留前一個安全狀態、標 `disputed`，不採最新覆蓋（核實計畫 §5.2）。
- 自動結案以單一 transaction 執行：比對版本 → 寫欄位 → 寫 `spot_field_verifications` → 結案 → 寫稽核（actor 記為系統，附參與審核者 ID）。版本衝突沿用 `admin_resolve_report` 的欄位級語意：只有本次寫入的欄位在提案送出後被改過（`base_spot` 與現值不同）才以 `40001` 拒絕並重置任務，無關欄位的變動不算衝突。
- 審核票的限流與回報分開計數（`review_rate_limit_events` 或 `rate_limit_events.kind`），否則 L2／L3 的每日任務上限永遠達不到，審核也會吃掉回報額度。

### 5.2 信任等級

| 等級 | 取得（自動，除 L4 另註） | 審核能力 | 其他 |
| --- | --- | --- | --- |
| L0 新車友 | 登入，帳齡 < 7 天或未完成新手任務 | 可做任務但**不計票**（訓練模式，只做黃金任務，見 §5.4） | 回報權重依帳齡、同現行（< 7 天 0.25，≥ 7 天 1）；每日回報 10 筆、任務 10 件 |
| L1 車友 | 帳齡 ≥ 7 天、新手任務 ≥ 5 件且黃金任務準確率 ≥ 80%、近 180 天無濫用 | 低風險計票；高風險的「3 名獨立車友」計數 | 回報權重 1；每日回報 10 筆、任務 10 件 |
| L2 熟手 | 點數 ≥ 100、審核任務 ≥ 20 件、準確率 ≥ 85% | 中風險計票 | 可標 `disputed`；每日回報 20 筆、任務 20 件 |

- 準確率＝「與最終結果一致的審核票」÷「已有最終結果的審核票」，黃金任務計入。
- 降級自動：準確率跌破門檻或翻案罰分累積即降一級；濫用（管理員標記）直接回 L0 並凍結 180 天；預檢連續三日達每日 3 次 reject 只凍結升級 7 天，不降級（§5.8）。
- L3、L4 存 `app_metadata.role`（`verifier`／`guardian`），由 service role 依 standing 表寫入；JWT 內就能判斷，與 `is_admin()` 同機制。因為降級後 JWT 在刷新前仍帶舊角色，`confirm_evidence` 與 `guardian_resolve_dispute` 在伺服器端另以 `contributor_standing` 二次檢查。#81 的 `contributor_role` 只認 `admin`，`verifier`／`guardian` 在回報者標示上仍是 `rider`，這是預期行為。
- 每日回報筆數沿用 `apply_report` 的每帳號限流（需改為依等級讀取上限，每 IP 30 筆不變）；任務件數是獨立計數。

### 5.3 遊戲化：點數、等級、徽章、排行榜、任務

**點數只獎勵事後證明正確的行為，並且可以扣回。**

| 行為 | 點數 | 說明 |
| --- | --- | --- |
| 修改建議被採納 | ＋10 | 採納時發放 |
| 新增停車點通過存在核實 | ＋20 | 兩名獨立 L1＋確認後發放 |
| 照片證據被 L3 確認且用於核實 | ＋5 | 照片通過隱私處理後才計 |
| 審核票與最終結果一致 | ＋3 | 結案時發放；「無法判斷」不加不扣；不同意票使案件升級後被證實正確者同樣 ＋3，避免「全投同意」最划算 |
| 貢獻後來被官方資料證實 | ＋5 | 官方點覆蓋層被新官方值證實（§5.6 第 3 點）、或與規則矛盾的觀察在規則更新後成立（§5.7）；只給成立時間早於新官方資料 `effective_date` 者，每人每月上限 3 次 |
| 黃金任務答對 | ＋1 | 不公開哪些是黃金任務 |
| 自己的貢獻在 90 天內被翻案 | －15 | 扣回原點數再罰 5 |
| 參與的社群結案被抽查或翻案推翻 | －3 | 同意票各扣 3 並降低準確率；抽查推翻與 `disputed` 經管理員裁決相反都適用 |
| 黃金任務答錯 | －5 | 並降低準確率 |
| 被標記濫用 | 清零 | 回 L0 並凍結 |

限制：每人每日點數上限（建議 60）；同一停車點每人每 90 天最多計一次審核點數；同一提案者的建議每月派給同一審核者不超過 3 件。

**等級**就是 §5.2，顯示為名稱與徽章，不顯示原始點數給他人。

**徽章**（非排名、可累積）：縣市首筆核實、連續 4 週有審核、100 件任務零翻案、照片證據 20 張被採納、協助結案一件 `disputed`。徽章不給點數，只給辨識。

**排行榜**：每月、每縣市，只列選擇加入的 L2＋，顯示 `display_name`（#83）與等級，不顯示貢獻的地點；每月重置，另有「本月最準確」榜（準確率，需 ≥ 20 件）與「本月最多」榜並列，避免只獎勵量。

**任務**：「本週你所在縣市有 N 件待審」「這個停車點需要第 3 位確認」；新手任務引導完成 5 件黃金任務。第一版只做 App 內的任務列與貢獻頁提示；伺服器推播需另加 FCM／APNs（既有 `lib/core/notifications.dart` 只是本機排程的停車提醒，沒有伺服器推播），上線後頻率上限每日 1 則。

**不做的事**：不做每日簽到、不做連續登入獎勵（製造無意義操作）、不把點數換成金錢或實物（§0 第 8 點）、不在地圖標記或資格橫幅上顯示任何等級或點數。

### 5.4 防刷與品質控制

| 手段 | 做法 |
| --- | --- |
| 黃金任務 | 管理員已確認答案的案件混入任務流（約 10%），用來量準確率與擋機器式點擊；題庫約半數是「應不同意」或「無法判斷」的案例，否則量不出同意偏誤；答案不公開，定期更換 |
| 結果綁定 | 點數在結案時發放、翻案時扣回；刷量沒有結果就沒有點數；不同意票被證實正確同樣加分 |
| 獨立性 | 沿用 `apply_report` 的同 IP／裝置檢查與帳齡；同 IP 的多票只算 1 票，不把 IP 當身分（核實計畫 §5.2） |
| 共謀偵測 | 以滾動 90 天統計：兩個帳號共同出現 ≥ 15 件任務且投票一致率 ≥ 95%，或同一提案者的建議被同一審核者同意 ≥ 10 件 → 列入風險旗標，點數暫緩發放，由管理員檢視；門檻依資料調整 |
| 派任務條件 | 任務只派給「目前地圖範圍在該縣市」的使用者；這是提高在地性的 UX 條件，地圖範圍由客戶端自報、可偽造，**不是**防刷手段；不要求也不儲存精確位置 |
| 冷卻與上限 | 每日任務上限（L1 10、L2 20、L3 30，與回報分開計數）、每日點數上限、同點位 90 天一次 |
| 抽查 | 管理員每月隨機抽查社群結案的 5%（穩定後 2%，案件少時每月至少 30 件）；不合格即翻案並扣分 |
| 翻案率閘門 | 依欄位類別、滾動 90 天批次統計，樣本 ≥ 100 件才生效；超過門檻的類別自動關閉共識結案，退回管理員，直到連續兩個批次低於門檻 |
| 申訴 | 被扣分者可申訴一次；L4 初審、管理員終審 |

### 5.5 管理員的 5% 是什麼

1. 禁區案件（§5.1）。
2. `disputed` 經 L4 初審仍無法定案者。
3. 申訴終審。
4. 隨機抽查（這是翻案率與抽查不合格率的資料來源，不是可省略的工作）。
5. 調整門檻、黃金任務、撤銷角色、處理共謀旗標。

管理員不再逐案審核事實類欄位。若抽查顯示某類別品質不足，關閉該類別的社群結案，讓它暫時回到管理員，這是設計內的退路，不是失敗。

### 5.6 官方點的資料修改核實模式（決定）

**現況與問題。** 官方點（`official_heavy_spots`，1,497 筆）的修改建議只能由 `admin_resolve_report` 採納，採納會直接改寫官方欄位。`tool/import_mymaps.py` 的 `official_sql()` 以 `on conflict(id) do update set` 覆寫全部 `OFFICIAL_COLUMNS`（名稱、座標、縣市、型式、`fee_note`、車種旗標、來源欄位，以及入口說明、停車指引、分區等細節欄位）；`hidden`、`effective_date` 不在更新清單，`fee` 與 `photo_urls` 不在匯入欄位。所以今天管理員採納的任何修改（除隱藏外），下次重新匯入就會消失，也分不出「哪個值是官方說的、哪個是我們改的」。核實計畫 §4.4 要求「社群證據只能形成修改提案，不可自行改寫官方來源與 `source_url`」，但沒有說提案採納後要存在哪裡。

**決定：官方值不可寫，社群核實存覆蓋層，衝突進爭議。**

1. **官方值只由匯入與管理員寫入。** `official_heavy_spots` 的欄位代表「官方資料說什麼」，社群結案永遠不改它；管理員也只在「核對官方來源後確認官方資料本身有誤或已更新」時直接改，否則同樣寫覆蓋層。
2. **社群核實的結果存成 `official_spot_overlays`**（§6），以 `(spot_id, field_key)` 為鍵，記錄當時的官方值快照、社群值、確認人數、證據、`verified_at`、`valid_until`、狀態。公開 view 把覆蓋層以 `community_overrides` 併入官方點，App 在詳情頁**並列顯示**「官方：X」與「現場回報：Y（N 位車友確認・日期）」，不以社群值取代官方值。
3. **官方值變動時覆蓋層自動失效。** 重新匯入或管理員改官方值後，若新官方值與覆蓋層快照不同：新值等於社群值 → 覆蓋層標 `confirmed_by_official` 結案（參與者加點，見 §5.3 補充）；新值不同於社群值 → 覆蓋層標 `superseded`、產生重新核實任務。與 #84 trigger「欄位變動即核驗失效」同一語意。反向也成立：一旦官方點有 `active` 的覆蓋層聲稱**型式或位置**與官方不符，該點所有 `source_kind='community'` 的車種核實立即失效，#85 §5.2 例外的「型式與位置已由可信來源核實」前提不再成立，直到管理員核對來源後定案。
4. **依欄位決定誰能結案**：

| 欄位群 | 官方點的欄位 | 社群能做什麼 | 核實方式 | 結案者 |
| --- | --- | --- | --- | --- |
| 身分與來源 | `source_url`、`source_name`、`source_id`、`license_note`、`effective_date`、`hidden` | 不能提案改值；「已不存在」只能回報 | 重新匯入、管理員核對來源 | 匯入／管理員（禁區） |
| 官方記載的事實（C 類） | `name`、`address`、`road_segment`、`city`、`district`、`lat`／`lng`（≤ 150 m）、同類內 `space_type`、`facility_type`、`fee`／`fee_note`、`scooter_total` | 提案「現場與官方不符」並附建議值 | 中風險共識（3 票含 L2＋、0 反對）＋至少 1 張現場照片；`facility_type` 變更使該點車種核實失效（第 3 點） | 社群 → 覆蓋層；要改官方值本身 → 管理員核對來源 |
| 資料穩定性（B 類） | 位置偏移 > 150 m、`space_type` 跨路外／路邊、與其他點重複、已不存在 | 提案並附照片 | 社群以 §5.1 B 類門檻預審（3 票含 L2＋＋L3 確認照片）；預審達成即讓該點車種核實失效並標 `reported_gone`（如適用） | 管理員確認後寫覆蓋層或改官方值 |
| 社群補充欄位 | `entrance_note`、`parking_guide`、`note`、`special_rules`、`parking_zones`（名稱、指引）、照片 | 直接提案 | 低風險共識（2 票）；`parking_zones` 的 `access` 屬停放資格，依下兩列 | 社群 → 覆蓋層 |
| 停放資格，官方**未**明載 | 需要可機讀的「明載」旗標：匯入時依來源寫入 `vehicle_source jsonb`（例如 `{"heavy":"official"}` 或 `{"heavy":"inferred"}`），因為 `official_heavy_spots.heavy_allowed` 是 `not null default true`，無法用 null 表示未明載。未明載＝旗標非 `official`。**只適用 `space_type='offStreet'` 且 `facility_type` 來自官方資料**的點；路邊官方點（例如預設的 `heavyOnly` 重機格）依縣市規則判定，不開放社群核實車種。**回填完成前不開放**（§0 第 9 點）：匯入工具補上旗標並回填既有 1,497 筆之前，官方點車種欄位一律視為本表下一列處理 | 回報業者規則 | #85 §5.2 例外（3 名獨立車友＋L3 確認的入口公告照片；型式與位置由官方資料提供，但不得有 `active` 的型式／位置覆蓋層） | 社群 → `spot_field_verifications`（`source_kind='community'`） |
| 停放資格，官方**已**明載 | `vehicle_source` 為 `official`（例如臺北市大型重機格數、36 處試辦場域） | 只能回報「現場與官方不同」 | 不產生覆蓋層；達 3 票即標 `disputed`，資格顯示依 #85 §3.4 降為「回報不一致，待確認」 | 管理員（核對官方公告後改官方值或駁回） |
| 已不存在／封閉 | — | 回報撤除、施工、封閉並附照片 | 臨時封閉（有截止日）為 C 類中風險 → 覆蓋層 `closure`；永久撤除為 B 類預審 → 覆蓋層 `existence='reported_gone'`：詳情顯示「車友回報已撤除」、搜尋排序後移、地圖維持顯示 | 標示：社群；`hidden`：管理員 |

5. **資格判斷的安全語意不變。** 官方明載「可停」而社群回報「不可停」：不覆蓋、不隱藏，顯示為「回報不一致，待確認」直到管理員裁決（保守方向只會讓騎士少停，#59）。官方明載「不可停」而社群回報「可停」：同樣只標爭議，絕不因票數變成可停。官方未明載時的社群核實結果只能讓顯示從「待確認」變成「社群核實可停／不可停（來源：車友）」，與官方核實分開標示。
6. **點數**：官方點覆蓋層的採納與翻案依 §5.3 同表計分；覆蓋層後來被官方資料證實（第 3 點）另加 ＋5，鼓勵「比官方更早發現變更」，但只給覆蓋層成立時間早於新官方資料 `effective_date` 的案例，且每人每月上限 3 次，避免預判官方更新刷分。
7. **匯入流程配合**（Admin Web P6）：差異試算除了官方值差異，另列「有覆蓋層的欄位」與「官方新值是否與社群值一致」，由管理員一次確認；匯入 SQL 不再 `do update set` 全部欄位，改為只更新官方欄位並保留 `hidden` 與覆蓋層。
8. **不在本模式內**：縣市規則、`city_rules`、官方點的新增（仍由匯入或管理員建立）、把社群點「改為官方點」（`admin_promote_spot`，管理員）。

### 5.7 法規預審引擎

**定位。** A 類（法規）不開放社群結案，但 A 類每件的成本最高：管理員要查公告、對生效日、判斷是規則過期還是現場例外。法規預審引擎做的是 B 類社群預審對 A 類做不到的事：用**現行規則資料**自動回答能回答的提案、把回答不了的整理成附引用的案件、把新公告整理成可確認的規則草稿。引擎**不發布規則、不改資格判斷、不解釋法律**，所有輸出都是草稿或引用，由管理員結案。

**三個面向。**

1. **提案端：入口預審。** 任何涉及法規結論的提案（路邊格位的車種資格、「這一區重機可停／不可停」；限時或斜停規則目前沒有結構化 `field` 鍵，需新增後才能預審）在進 `moderation_queue` 之前，先用目前生效的 `city_rules` 版本計算「規則說什麼」。這裡**不能直接重用 `eligibility()`**：它的輸出混入點位信任狀態（未確認社群點一律 `unverified`、`offStreet` 不看規則、限時格轉 `conditional`），四態對不上引擎需要的結論。要從 `lib/domain/eligibility.dart` 抽出純規則函式 `ruleVerdict(rule, ruleSpaceType(spaceType), district)` → `open / conditional(restriction) / closed / noRule / unknownDistrict`，Dart 與伺服器端（SQL 或 Deno）各一份實作，以 `assets/rules/parking_rules.json` 為共同測試向量保證兩邊一致。`conditional` 與 `unknownDistrict` 都視為「規則無法單獨回答」，與提案值不衝突時歸入一致、衝突時歸入矛盾。三種結果：

| 引擎結果 | 處理 | 對回報者 |
| --- | --- | --- |
| 提案與規則一致（例如回報黃牌可停，規則本就開放） | 不建 A 類案件；若回報者帳齡 ≥ 7 天且通過獨立性檢查，觀察存為該規則的**現場佐證** `rule_evidence`（含規則快照與行政區），更新該縣市規則的最近佐證時間 | 即時回覆「依 ○○市 ○年○月公告已開放」。**不發點、不計準確率**：一致不代表核實，否則對每個格位重複回報即可刷分與灌水佐證 |
| 提案與規則矛盾 | 建 A 類案件，自動附上：規則版本、生效日、`source_url`、矛盾點、同縣市同型式近 90 天的矛盾觀察數、該點是否有 `signage` 限制；初步分類為「疑似現場標示例外」（規則 `restriction=signage` 時）或「疑似規則已變更」 | 回覆「與目前規則不符，已送管理員查證」；若日後規則確實更新且觀察早於公告生效日，依 §5.3「被官方證實」一列 ＋5，每人每月上限 3 次 |
| 該縣市／車種／型式沒有生效規則（`noRule`） | 不逐案建案；累積到「缺規則」清單，按縣市與型式計數 | 回覆「此地區尚無規則資料，已記錄」 |

   同一縣市同型式的矛盾觀察在 90 天內達到門檻（建議 5 件、來自 3 名以上獨立 L1＋；等級系統上線前以「帳齡 ≥ 7 天且獨立性風險低」代替）→ 自動產生一件「規則複查」任務給管理員，附全部觀察與照片；這是 A 類案件的聚合入口，避免管理員逐件看。

2. **法規端：規則變更預審。** 管理員在 Admin Web P5 規則頁貼入公告（網址、文字或 PDF），引擎產出：
   - **結構化草稿**：`city`、`vehicle`、`allowed_space_types`、`conditional_space_types`、`districts`／`district_space_types`、`restriction`、`can_use_two_spaces`、`fee_note`、`effective_date`、`source_url`、`exceptions` 文字；`version` 由伺服器遞增（ADMIN_WEB.md P5），不在草稿內。抽取可用 LLM 輔助，但輸出只是草稿，每個欄位旁顯示抽取依據的原文片段，管理員逐欄確認。
   - **一致性檢查**：資料庫約束（例如 `city_rules_restriction_required`）、與現行版本的欄位 diff、生效日不早於現行版本（同生效日的更正性修訂需填更正理由）、`assets/rules/parking_rules.json` 是否需同步（P5 規劃中的 `tool/export_rules.py`）。`city_rules` 目前以 `(city, vehicle)` 為主鍵、版本原地覆寫、沒有歷史表；引擎第一個 migration 需加 `city_rules_history`（§10 第 16 點），否則 `rule_evidence.rule_version` 事後無法還原當時規則。
   - **影響分析**：套用草稿後，該縣市有多少點位的 `EligibilityStatus` 會改變，按型式與車種列出 before／after 與數量；哪些官方點 `vehicle_source='official'` 的值與新規則衝突；哪些既有 A 類案件會因此自動結案。
   - **產出**：規則新版本的 SQL 草稿與 JSON 同步 diff，管理員確認後發布（Admin Web P5 規則頁與伺服器端版本遞增是 §5.7 面向 2 的前置依賴，目前尚未實作）；發布時引擎回頭結掉被新規則解答的 A 類案件，並對早於公告生效日的矛盾觀察依 §5.3「被官方證實」一列加點。

3. **巡檢：來源變更與到期。** 定期抓取 `city_rules.source_url` 與官方點 `source_url` 的內容，抽出正文後雜湊，變更即建「來源變更」任務；動態頁面或社群平台貼文（例如高雄規則的 Facebook 來源）無法穩定雜湊，只做到期提醒。規則或公告有載明期限者（例如試辦期）到期前 30 天建「到期複查」任務。這面向只產生任務，不改資料。

**與現有程式的關係。** 入口預審依賴既有的 `city_rules` 資料與從 `eligibility()` 抽出的純規則函式（上文），在 `submit-report` 路徑上執行一次；抽函式與共同測試向量是階段 1 的前置工作。規則草稿與影響分析落在 Admin Web P5（P5 尚未實作，是面向 2 的前置依賴）；巡檢落在階段 3。

**護欄。**
- 引擎結果永遠是「規則目前這樣說」，不是「現場合法」；回覆文案沿用 App 既有的「請以現場標誌標線為準」。
- 與規則一致的觀察不改變任何資格顯示，只更新佐證時間。
- 矛盾觀察再多也不自動改規則；聚合門檻只產生管理員任務。
- LLM 抽取的草稿不得直接寫入 `city_rules`；沒有原文片段對應的欄位不可確認。
- 影響分析用唯讀查詢，不寫任何資料。

**指標。** A 類提案被引擎判為與規則一致、不進管理員佇列的比例（一致率，目標 ≥ 50%）；缺規則率另列，不算回答；管理員處理一件 A 類案件的中位時間；規則複查任務數與其中確實導致規則更新的比例；來源變更任務的誤報率。

### 5.8 預檢模組

**定位。** 在提案、新增停車點與審核票進入任何佇列之前，用**確定性規則**檢查「欄位彼此是否矛盾」與「內容或行為是否違規」。它接在既有 `submit-report/validate.ts`（型別、白名單、座標範圍、長度）之後、法規預審（§5.7）與 A／B／C 分類之前。目的有三：把明顯錯誤在送出當下擋回給回報者修正，不浪費審核人力；把可疑但不確定的提案標上風險旗標，讓後面的共識規則加嚴；把政策不允許的提案直接拒絕並說明原因。

**處理流程。**

```text
validate.ts（結構）→ 預檢（組合／內容／行為）→ 法規預審 §5.7 → 分類 A/B/C → 建案件與任務
                      ├─ pass：照常進入下一步
                      ├─ fix：拒收並回傳可修正的欄位與原因（App 即時顯示）
                      ├─ hold：進入下一步，但寫入 risk_flags（語意依對象不同，見下）
                      ├─ reject：拒收並說明；連續觸發計入濫用訊號
                      └─ reroute：改送正確的流程（路邊車種資格 → §5.7；備註夾帶資格宣稱 → 資格表單）
```

`hold` 依對象有三種語意：**提案**進佇列但共識門檻加 1 票、且 L0／L1 提交的照片不計入門檻（§0 第 7 點）；**審核票**照常記錄但不計入共識；**照片**不計入任何門檻。`precheck_rules` 以 `subject_kind` 區分。

規則定義在一份版本化的清單（`precheck_rules`），Flutter 與 Edge Function 共用同一份鍵值（與 `validate.ts` 的 `spaceTypes`／`suggestionFields` 和 `lib/models` 共用鍵值的做法相同）：App 端只做即時提示，Edge Function 端才是強制點，不信任客戶端的預檢結果。

**四組規則（初版清單，數值待校準）。**

| 組 | 規則（代碼） | 動作 |
| --- | --- | --- |
| 1 異常組合：型式 | `offStreet` 卻帶 `facility_type='roadside'`；非 `offStreet` 卻帶 `facility_type` 為 `multiStorey`／`underground`／`surface` 或帶 `parking_zones`；`heavyOnly` 卻 `scooter_allowed=true`（`validate.ts` 只做單欄位型別，這些跨欄位組合今天都放行） | fix |
| 1 異常組合：車種 | `parking_access='noMotorcycle'` 卻 `scooter_allowed` 或 `heavy_allowed` 為 true；`parking_access='heavyOnly'` 卻 `scooter_allowed=true`；`parking_zones` 全部 `noMotorcycle` 但頂層 `scooter_allowed=true`；`scooterOnly` 卻 `heavy_allowed=true` | fix |
| 1 異常組合：費率 | `fee.heavy.mode='same_as_scooter'` 但沒有 `fee.scooter`；`daily_cap < amount`；`hourly` 且 `amount=0`（應填 `free`）→ fix。結構與文字矛盾（`scooter` 與 `heavy` 都 `free` 但 `fee_note` 含「元／小時」且不含「汽車」）只提示不擋，因為「前 30 分鐘免費」「機車免費、汽車每小時 30 元」都是合法寫法，`fee` 只涵蓋機車車種 | 結構：fix；文字：hold（列為誤攔率優先觀察） |
| 1 異常組合：位置 | 座標反查的縣市／行政區與填寫不同（Edge Function 端呼叫國土測繪中心 `TownVillagePointQuery`，與 `lib/core/town_lookup.dart`、`tool/import_mymaps.py` 同一端點；反查失敗或逾時時放行並寫 `risk_flags`，不得因外部服務不可用擋回報；同時把「台／臺」等寫法正規化為 22 縣市正式名）；座標與同名既有點 > 2 km；與不同型式的既有點座標完全相同（同型式 15 m 內 `apply_report` 已回 `duplicate_id`）；位置移動提案 > 150 m 卻未附照片 | 縣市不符：fix；其餘：hold（同座標跨型式另提示可能為型式爭議） |
| 1 異常組合：時間 | `observed_at` 在未來或早於 90 天；臨時封閉的截止日早於今天（兩個欄位目前都不存在，隨核實計畫 P2 的 `spot_observations` 新增） | fix |
| 1 異常組合：提案本身 | 「已不存在」同時帶其他欄位修改；`proposed` 與目前值完全相同；同一人對同一點同一欄位 24 小時內重複提案（`idempotency_key` 以外的內容變體）。後者取代今天 `moderation_queue` 的 `(source_id, reason)` 唯一索引＋`on conflict do nothing` 靜默丟棄行為（核實計畫 §4.4 要求改掉），fix 回應要告知「已有同案」 | fix／合併至既有案件 |
| 2 違規：政策 | 對路邊格位提車種資格 → reroute 至 §5.7（A 類）；官方點的 `source_url`、`source_name`、`effective_date` 修改與官方點的 `status` → `validate.ts` 的 `proposed` 白名單今天已回 400，預檢只補 `precheck_results` 記錄；對其他 A 類欄位的 `proposed` 值 → reject | reject／reroute |
| 2 違規：內容 | 名稱或備註含網址、電話、Email、車牌格式、身分證格式 → 個資與廣告；`note`／`entrance_note` 以機車或重機為主詞出現「可停／不可停／合法／違規」等資格宣稱 → 導向資格表單（「汽車格不可停機車」這類法規用語不攔）；全形重複字元或表情符號超過比例；名稱為「停車場」「測試」等占位詞 | 個資：reject；宣稱：reroute；其餘：fix |
| 2 違規：照片 | 同一張照片雜湊在 30 天內用於 ≥ 3 個不同點位；照片檔內 EXIF 拍攝時間與 `observed_at` 差 > 30 天（處理前讀取，處理後移除）。照片上傳本身尚未實作，隨核實計畫 §4.3 一併 | hold（照片不計入門檻） |
| 3 行為異常 | 同一帳號 10 分鐘內對相距 > 50 km 的兩點送出「現場觀察」；同一帳號 1 小時內對 ≥ 10 個點位修改同一欄位為同一值；帳齡 < 7 天且 1 小時內 ≥ 5 筆；同裝置在 24 小時內出現 ≥ 3 個帳號；審核票在任務派出後 < 5 秒送出 | hold；同一帳號當日 reject 達 3 次 → 當日後續提案 reject 並寫濫用訊號（hold 不計入這 3 次） |
| 4 與現況衝突 | App 送出時帶它看到的 `base_updated_at`（`validate.ts` 需新增此欄位），與現值不同即提早觸發 §5.1 的欄位級衝突；目標點位已隱藏或已被合併 | fix（要求重新載入） |

**與其他機制的關係。**
- `hold` 寫入的 `risk_flags` 就是核實計畫 §4.1 `spot_observations.risk_flags` 的內容；審核任務頁對 L2＋顯示旗標名稱（不顯示給 L0／L1，避免教人繞過）。
- 預檢 `reject` 不扣點（提案沒有進入系統），但同一帳號每日 reject 次數計入 §5.4 的濫用訊號；連續三日達每日 3 次 → 凍結升級 7 天（比管理員標記濫用的「回 L0 凍結 180 天」輕一級，兩者都寫入 `contributor_standing.frozen_until`）。
- 群組 2 的「資格宣稱」不是拒絕，而是把人導向正確的表單。
- 行為異常 `hold` 套在舊 `vote` 路徑的存在確認時，對應的加嚴是 `apply_report` 的 `v_count>=2` 門檻加 1；這是舊路徑唯一需要改的地方。
- 被攔的提案不入庫，`precheck_results` 存去識別後的觸發欄位快照（只存觸發規則用到的欄位值，不存座標以外的個資），App 在攔截訊息旁提供「回報此攔截有誤」，這是誤攔率分子的來源；管理員在指標頁覆核。
- 預檢不做任何「判斷對錯」：它只看欄位之間與政策之間的矛盾。一個自洽但錯誤的提案會照常進入共識流程。
- 每條規則可由管理員單獨停用、調整參數；每次觸發寫 `precheck_results`，供計算誤攔率。

**護欄。** 規則必須是可解釋的確定性檢查，回傳的原因文字要讓回報者知道改哪個欄位；不用機器學習模型做 reject（可用於 hold 的輔助訊號，但須另列決策）；個資偵測只做格式比對、不外送內容；預檢結果與風險旗標不進公開 view。

**指標。** 預檢攔截率（fix＋reject 占送出數）；誤攔率（被攔後申訴或管理員覆核認定無誤的比例，目標 ≤ 5%）；`hold` 案件最終被翻案的比例相對一般案件的倍數（驗證旗標有效）；各規則的觸發數與誤攔數（決定停用或調參）。

## 9. 分階段與依賴（每階段以指標驗收）

```text
階段 0（可立即，與核實計畫 P1 並行；不改權重，不發點數）
  ├─ moderation_queue.resolution_kind、risk；Admin Web 駁回必選
  ├─ my_contributions() + 貢獻頁「我的建議」

  ├─ 量測基線：每月案件數、管理員結案時效、回報者人數（LEAN UX 待驗證項）；已實作 admin_review_baseline()，見 §2.4
  └─ 修訂核實計畫 §1 不在範圍句與 §3.3 費率策略（#87 已合併）
階段 1（依賴核實計畫 P2：spot_observations、spot_evidence）
  ├─ review_tasks／review_votes／contributor_standing／point_ledger
  ├─ official_spot_overlays ＋ 匯入只更新官方欄位（§5.6；可先於遊戲化獨立交付）
  ├─ 法規預審引擎的入口預審與 rule_evidence（§5.7 第 1 面向；只依賴既有 eligibility 與 city_rules）
  ├─ 預檢模組其餘規則、precheck_rules／precheck_results、「回報此攔截有誤」、risk_flags 接入共識門檻（§5.8）
  ├─ vehicle_source 旗標：匯入工具寫入＋既有 1,497 筆回填（§0 第 9 點；完成前官方點車種欄位不開放社群核實）
  ├─ 從 eligibility() 抽出純規則函式 ruleVerdict 與共同測試向量；city_rules_history（§5.7 前置）
  ├─ 低風險類別共識結案（2 票）＋ 黃金任務 ＋ 點數
  ├─ L0–L2 自動等級；排行榜（選擇加入）
  └─ 驗收：低風險翻案率 ≤ 3%（第一個完整 90 天批次）、低風險類別的社群結案率 ≥ 50%

  ├─ 中風險共識結案（3 票含 L2＋）；disputed 流程
  ├─ L3 照片內容確認 → #85 §5.2 例外由社群完成
  ├─ L4 守護者、申訴、管理員抽查佇列、翻案 RPC
  ├─ 規則變更預審：草稿、一致性檢查、影響分析、發布（§5.7 第 2 面向；併入 Admin Web P5 規則頁）
  └─ 驗收：中風險翻案率 ≤ 5%、社群結案率 ≥ 80%、A 類引擎一致率 ≥ 50%
階段 3（依賴核實計畫 P4 指標）
  ├─ 指標頁、類別閘門自動化、共謀偵測
```

## 10. 待拍板決策

已決定的項目見 §0 決策紀錄（方向、覆蓋層模式、開放原則、指標分母、已不存在的預審門檻、`hold` 加嚴方式、點數不兌換、`vehicle_source` 先回填再開放、硬拒絕範圍、計畫修訂 PR、階段 0 另開 session）。以下為仍待拍板的項目：

1. **分段目標與時程**：50%／80%／95% 的月份數（建議 3／6／12 個月）。
2. **每票權重**：維持全部為 1（建議），或允許 L3 在中風險類別算 2 票（不建議，會重建多數決問題）。
3. **排行榜範圍**：每月每縣市、選擇加入（建議）；是否要全國榜。
4. **黃金任務來源與比例**：管理員標記已確認案件，約 10%，半數為應不同意；誰負責維護題庫。
5. **L4 的產生方式**：L3 滿 90 天＋管理員確認（建議），或純管理員授予。
6. **抽查比例**：起始 5%，穩定後 2%，案件少時每月至少 30 件。
7. **點數表數值**（§5.3）與每日上限 60 的初值。
8. **是否修訂 `ADMIN_WEB.md`**：多層級角色、P5 規則頁納入草稿與影響分析、P6 匯入差異試算納入覆蓋層、P7 使用者頁、指標頁、B 類「已預審」佇列。
9. **「已不存在」的顯示降級**：`reported_gone` 是否要在地圖標記上有視覺差異（建議只在詳情與排序處理，地圖四態不變）；隱藏維持管理員，不修訂 #59。
10. **B 類預審率目標**（§2.1 建議 ≥ 80%）與管理員否決率的警戒值。
11. **法規預審引擎的 LLM 抽取**：規則草稿是否以 LLM 輔助抽取（建議是，但每欄位須對應原文片段且管理員逐欄確認），或只提供表單與原文並排。
12. **與規則一致的提案是否建案**：本文建議不建案、只存佐證並即時回覆；若希望留痕供稽核，可改為建案並自動結案。
13. **規則複查門檻**：90 天內同縣市同型式 5 件矛盾觀察、3 名以上獨立 L1＋（初值，待校準）；等級系統上線前以「帳齡 ≥ 7 天且獨立性風險低」代替 L1＋。
14. **預檢是否使用機器學習訊號**：本文建議第一年只用確定性規則；若要用（例如照片是否為停車場景），只能作為 `hold` 的輔助，不能 `reject`。
15. **行為異常門檻初值**（§5.8 第 3 組）與「每日 3 次 reject 即封鎖當日後續提案」是否過嚴。
16. **`city_rules` 歷史表**：引擎需要「當時版本說什麼」；採 `city_rules_history` 表，或在 `rule_evidence` 存規則快照（建議前者，一次 migration）。
17. **審核票與照片的 `hold` 語意**：提案的 `hold` 已決定為門檻加 1 票；審核票 `hold` 為該票不計入共識、照片 `hold` 為不計入任何門檻（§5.8），是否同意。
