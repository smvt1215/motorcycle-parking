# 貢獻等級制可行性研究

> 狀態：研究結論，尚未拍板／尚未實作  
> 日期：2026-10-25（Asia/Taipei）  
> 盤點基準：`main` commit `40d96db`（含 #76）；另參考審核中的 #81、#83、#84、#85  
> 依據：[社群共筆與停車資訊核實機制](COMMUNITY_VERIFICATION_PLAN.md)（以下稱「核實計畫」）、[Admin Web 計畫](ADMIN_WEB.md)、[專案總計畫「社群回報機制」](PLAN.md#社群回報機制)  
> 性質：只回答「要不要做、能做成什麼樣、先後順序」。本文不更改程式，也不代表核實計畫已採納等級制。

## 1. 結論

**可行，但只能做成「信任等級」，不能做成「遊戲化等級」。**

- 核實計畫 §1 明列「公開使用者排行榜、可交換點數等遊戲化機制」不在範圍；原則 2 要求「不以多數票取代法規」。點數、徽章、排行榜式的等級與這兩條衝突，不建議。
- 但系統現在就已經有一套**沒有名字的兩層信任等級**（§2）：帳齡 7 天以下的投票權重 0.25、以上為 1；管理員是另一個布林角色。核實計畫 §5.2 的「合格帳號」「獨立性風險低」、§4.1 的 `account_age_bucket`／`risk_flags`，都是信任等級的輸入。
- 真正產生需求的是 #85：管理員無法核驗全國點位，路外場站業者規則改由「多名獨立車友＋1 張**經審核者確認內容**的入口公告照片」核實，而審核者被寫成「管理員或**經授權的審核角色**」。今天的權限模型只有 `is_admin()`，沒有這個角色。等級制若要做，核心交付就是這個介於車友與管理員之間的「審核者」層，以及決定誰算「獨立合格車友」的自動等級。
- 等級**只能影響三件事**：一筆觀察算不算合格的獨立觀察、能不能執行特定審核動作、每日限流額度；另外只對審核者與管理員顯示回報者等級作為參考標示。等級**不能**把任何單票的權重提高到 1 以上，不能自動把車種資格變成「可停」，不能公開排名。
- 冷啟動期（使用者少、採納紀錄少）等級制幾乎降不了管理員負載；審核者仍需管理員人工授予。這是誠實的限制，不是反對理由。

建議分三階段推進（§7）：先替既有兩層命名並補上使用者可見的貢獻統計與駁回分類（不改任何權重）；等核實計畫 P2 的 `spot_observations` 上線後再自動計算等級；最後配合照片證據與 Admin Web P7 使用者頁推出審核者角色。

## 2. 現況盤點：系統裡已存在的隱性等級

| 身分 | 判定方式（程式位置） | 現有能力 | 現有限制 |
| --- | --- | --- | --- |
| 匿名／未登入 | `AppStore.canReport` 為 false（範例模式除外） | 瀏覽、收藏、停車紀錄 | 不能回報（PLAN.md 權限分級） |
| Google／Apple 登入，帳齡 < 7 天 | `apply_report`：`v_qualified := created_at <= now() - 7 days`（規則出自 `202610240010_vote_safety.sql`，最新定義在 `202610250030_report_details.sql`，邏輯相同） | 新增停車點、修改建議、舊 `vote` | 投票 `qualified=false`、權重 0.25；每日 10 筆（帳號）／30 筆（IP） |
| 帳齡 ≥ 7 天 | 同上 | 同上 | 權重 1；與原回報者同 IP 或同裝置時降回 0.25；兩名合格者才能確認存在 |
| 管理員 | `is_admin()`：`app_metadata.role='admin'` 且 `aal2`（`202610240003_admin_backend.sql`） | 審核、編輯、隱藏、改為官方點、（#84）核驗車種 | 單一布林角色；ADMIN_WEB.md 明列「多層級角色」不在範圍 |

也就是說，等級制不是從零開始，而是把 **2＋1 層**命名、補上行為紀錄做為輸入、再加一個審核者層。

### 2.1 已有、可用來計算貢獻的資料

| 資料 | 位置 | 可算出 |
| --- | --- | --- |
| 建立的社群點 | `community_spots.user_id` | 新增數、其中被隱藏／改為官方點的數量 |
| 修改建議與結果 | `moderation_queue.reporter_id`、`status`（`pending/accepted/rejected/closed`）、`resolution_note` | 送出數、採納數、駁回數 |
| 舊投票 | `spot_votes.user_id`、`qualified` | 歷史投票數 |
| 管理操作 | `admin_audit_log`（`resolve_report`、`create_spot`、`update_spot`、`hide_spot`…） | 誰採納了誰的建議、何時 |
| 限流 | `rate_limit_events` | 活躍度（達上限的請求會回滾、不留紀錄，所以推不出「撞上限幾次」，需要時另記被拒事件） |

### 2.2 現在缺的

- **使用者看不到自己的貢獻。** `moderation_queue` 只有 `admin_read_moderation` 一條讀取政策；沒有「本人可讀自己 `reporter_id` 的列」或對應 RPC。貢獻頁（`lib/features/contribute/`）只列目前地圖範圍內的停車點，沒有「我送出的建議／狀態」。
- **駁回沒有分類。** `rejected` 只有自由文字 `resolution_note`，分不出「判斷錯誤」「重複」「濫用」。拿採納率算等級時，一個誠實但判斷錯的車友和灌水帳號會被一視同仁。
- **沒有使用者資料表。** #83 把顯示名稱與頭像放在 `raw_user_meta_data`（使用者可自改）；#81 把名稱快照到 `community_spots.contributor_name`。等級屬於伺服器判定的資料，**不能放 `raw_user_meta_data`**，只能放 `app_metadata`（service role 寫）或獨立表。
- **沒有中間角色。** `is_admin()` 是布林；#84 的核驗 trigger、`admin_resolve_report`、`admin_upsert_spot`、`admin_set_spot_hidden` 全部以它為唯一閘門。

## 4. 設計選項

| 選項 | 內容 | 評估 |
| --- | --- | --- |
| A. 不做等級，只保留 `qualified` 布林 | 維持 7 天帳齡 | 最便宜，但滿足不了 #85 的審核者需求，也無法把「常被駁回的帳號」與「可靠車友」分開 |
| B. **信任等級＋人工授予的審核者**（建議） | 自動計算的 T0／T1／T2，加上管理員人工授予的審核者角色 | 與核實計畫一致；等級只決定「算不算合格觀察」與「能做哪些審核動作」 |
| C. 遊戲化等級 | 點數、徽章、排行榜、等級越高票越重 | 違反核實計畫 §1；誘發灌水；「資深者一票當三票」會重建多數決問題。不建議 |

### 4.1 外部先例（依各平台公開說明的一般印象，未逐一查證，不是本專案的量測）

- 維基百科的「自動確認使用者」以帳齡與編輯數自動解鎖權限，沒有排行榜；與本專案的 7 天規則同類。
- Stack Overflow 以聲望分級解鎖審核權限；聲望本身是公開排名。
- Google 地方嚮導以點數分級並公開等級；公開排名容易誘發以量取分。
- Waze 地圖編輯者的等級決定可編輯的範圍與道路類型，審核仍靠區域管理者人工。
- OpenStreetMap 沒有正式等級，人人可編輯，品質靠事後檢視工具與社群。

可以觀察到的共通點是：**自動解鎖的多是低風險動作，高風險動作仍靠人工授予的角色**。這與核實計畫「低風險逐步自動化、高風險人工把關」的原則一致。實作前若要引用，應補上各平台的說明頁連結。

## 5. 建議方案：信任等級

### 5.1 等級定義

| 等級 | 取得方式 | 能力 | 不能做 |
| --- | --- | --- | --- |
| T0 新車友 | Google／Apple 登入，未達 T1 條件 | 新增停車點、修改建議、附照片（照片待核實計畫 P2 的上傳流程） | 觀察權重 0.25（現行）；不計入存在核實與 #85 §5.2 例外的「獨立車友」 |
| T1 合格車友 | 帳齡 ≥ 7 天，且近 180 天沒有被標記為濫用的駁回（自動） | 觀察權重 1；計入存在核實與 #85 §5.2 例外的「多名獨立車友」 | 權重仍為 1，不因資歷加權 |
| T2 資深車友 | 近 365 天採納 ≥ N 則、採納率 ≥ P%、無濫用記錄（自動升、自動降；N、P 待校準，§8） | 每日限流提高；建議進入審核佇列時標示來源可靠度供審核者參考 | 權重仍為 1；不得自動核實任何欄位 |
| R 審核者 | 管理員在 Admin Web 人工授予；建議前提為 T2，資料不足期間由管理員裁量（§6、§8 第 8 點）；可撤銷 | 確認證據照片內容（#85 §5.2）、採納白名單內的低風險欄位（名稱、入口說明、停車指引；備註是否納入見 §8 第 7 點）、把案件標 `disputed` 送管理員 | 不能改法規、不能隱藏或恢復官方點、不能核驗車種為管理員等級、不能處理申訴 |
| A 管理員 | 既有 `is_admin()` | 全部 | — |

兩條硬規則：

1. **沒有任何等級的單筆觀察權重超過 1。** 等級只決定一筆觀察「算不算」，不決定它「值幾票」。否則核實計畫 §1 原則 2「不以多數票取代法規」會從後門被推翻。
2. **等級不改變 `EligibilityStatus` 的計算。** 車種資格的輸入只有官方資料與縣市規則、管理員核驗（#84 的過渡欄位，#85 §4.2 規劃日後遷入 `spot_field_verifications`）與有效期內的社群欄位級核實（#85 §3.4）；等級不在輸入之列。

### 5.2 護欄

- 不公開排行榜、不公開一般等級與採納數；只有本人與管理員可見。
- 審核者與管理員可考慮在詳情頁「資料與查核」區標示角色（例如「照片由審核者確認」），因為使用者需要知道核實來源；是否顯示人名依 #81 的名稱政策。
- 等級資料不進任何公開 view（`public_spots`、viewport RPC）。
- 不以 IP 唯一性當等級條件（核實計畫 §11 第 1 點）；同 IP／裝置只影響該筆觀察的獨立性，不影響等級。
- 審核者確認照片只代表「這張照片是這個場站的入口公告，內容與要核實的值相符」，不代表判定合法。文件與 UI 文案都要寫清楚。
- 審核者操作與管理員一樣寫入 `admin_audit_log`，並要求 `aal2`（照片可能含個資）。

### 5.3 資料模型（建議，實作時再定版號）

**新增私有表 `contributor_standing`**

- `user_id uuid PK`、`tier text`（`t0/t1/t2`）、`accepted_count int`、`rejected_count int`、`abuse_count int`、`last_accepted_at`、`computed_at`、`frozen_until timestamptz`（管理員暫停升級）、`updated_at`。
- 由 `admin_resolve_report` 與（P2 後）`spot_observations` 的 trigger 增量更新，再以每日重算修正漂移；或先只做每日重算，減少交易內工作。
- RLS：本人只能讀自己的列（`tier` 與計數），管理員全部；沒有任何 insert／update 政策，只由 security definer 函式寫。
- 審核者角色**不放這張表**，放 `app_metadata.role='reviewer'`，由 service role 寫入；原因是 JWT 內就能判斷、與 `is_admin()` 同一套機制、停權時 Admin Web P7 規劃中的 `admin-users` 能一起處理。

**既有表調整**

- `moderation_queue`：`rejected` 增加 `resolution_kind text`（`wrong/duplicate/abuse/other`），Admin Web 駁回時必選。這是等級制的前置，即使不做等級也值得。
- 未來的觀察寫入（核實計畫 P2 的 `spot_observations`）：合格判定改讀 `contributor_standing.tier >= t1`，表內沒有列時退回現行帳齡判斷，確保相容。舊 `vote` 路徑維持帳齡判斷不改，因為核實計畫 §4.4 與 §11 第 3 點已把它列為只保留相容、待淘汰。

**新函式**

- `is_reviewer()`：`app_metadata.role in ('reviewer','admin')` 且 `aal2`。
- `reviewer_confirm_evidence(p_evidence_id, p_supports boolean, p_note)`：寫 `spot_evidence.content_confirmed_by/at`，寫稽核；依賴核實計畫 P2 的 `spot_evidence`。
- `reviewer_resolve_report(p_id, p_decision, p_patch, p_note)`：只接受低風險欄位白名單（名稱、入口說明、停車指引；備註見 §8 第 7 點），其餘欄位以 `42501` 拒絕；內部沿用 `admin_resolve_report` 的版本衝突檢查。
- `my_contributions()`：回傳本人送出的建議、狀態、建立的停車點與目前等級；取代直接開放 `moderation_queue` 的讀取政策，避免 `base_spot` 等欄位外流。
- `admin_set_reviewer(p_user, p_grant boolean, p_note)`：授予／撤銷，寫稽核；Admin Web P7 使用者頁呼叫。

### 5.4 與 #84 trigger 的關係

#84 的 `community_spots_vehicle_verification` 以 `is_admin()` 判斷是否記錄核驗。審核者不是管理員，所以審核者採納低風險欄位時不會、也不該觸發車種核驗。審核者確認照片後，#85 §5.2 例外達成時寫入的是 `spot_field_verifications`（`source_kind='community'`），與 #84 遷入的 `source_kind='admin'` 列分開，並遵守 #85「不覆蓋較高來源」。

### 5.5 使用者介面

- 貢獻頁加「我的貢獻」：目前等級（T0／T1／T2 的中文名）、已採納、待審、被駁回各幾則，以及升到下一級還差什麼。資料來自 `my_contributions()`。
- 修改建議表單在 T0 時提示「帳號滿 7 天後，你的確認會計入核實」；不顯示權重數字。
- Admin Web 審核佇列在每則案件旁顯示回報者等級與採納率（僅管理員與審核者可見）。
- Admin Web P7 使用者頁：搜尋使用者、查看等級與計數、授予／撤銷審核者、凍結升級。

## 6. 風險與限制

| 風險 | 說明 | 緩解 |
| --- | --- | --- |
| 冷啟動 | 使用人數少、採納紀錄少，T2 很久沒有人；審核者只能由管理員從認識的車友中授予 | 階段 0 不依賴 T2；審核者授予以 T2 為「建議條件」而非硬條件，資料不足期間由管理員裁量（與 §5.1 一致，是否改為硬條件見 §8 第 8 點） |
| 採納率受審核積壓影響 | 管理員積壓越久，採納越慢，升級越慢；懲罰的是車友不是系統 | 只計已結案的案件；`pending` 不算分母 |
| 駁回原因混淆 | 「判斷錯」「重複」「濫用」不分，誠實車友被當灌水 | 先補 `resolution_kind`；只有 `abuse` 影響等級 |
| 女巫攻擊 | 養多個帳號滿 7 天即 T1 | T1 只是「算一票」，仍受同 IP／裝置獨立性檢查；T2 需真實採納紀錄，成本高 |
| 審核者被收買或自利 | 例如替特定場站確認照片 | 審核者不能處理自己送出的案件；每個核實保留證據與審核者 ID；管理員可撤銷，其已確認的核實依 §8 第 9 點決定回到 `disputed` 或保留 |
| 隱私 | 等級與採納數會揭露活動量與活動地區 | 只有本人與管理員可見；不進公開 view |
| 維運成本 | 多一套狀態機、多兩個 RPC、Admin Web 多一頁 | 階段化；每階段獨立 PR 與 pgTAP |
| 誤導使用者 | 「資深車友說可停」被當成合法保證 | 等級不出現在詳情頁的資格橫幅；資格只依 #85 §3.4 分層顯示 |

## 7. 分階段建議與依賴

```text
階段 0（可立即，與核實計畫 P1 並行，不改權重）
  ├─ moderation_queue.resolution_kind + Admin Web 駁回必選
  ├─ my_contributions() RPC + 貢獻頁「我的貢獻」
  └─ 文件：替 T0／T1 命名，說明 7 天規則
階段 1（依賴核實計畫 P2：spot_observations）
  ├─ contributor_standing 表、每日重算、本人可讀
  ├─ 新觀察的合格判定改讀 standing（相容退回帳齡；舊 vote 不改）
  └─ 自動 T2 與自動降級
階段 2（依賴 P2 的 spot_evidence 與 Admin Web P7）
  ├─ is_reviewer()、app_metadata.role='reviewer'
  ├─ reviewer_confirm_evidence、reviewer_resolve_report（白名單）
  ├─ admin_set_reviewer + Admin Web 使用者頁
  └─ #85 §5.2 例外改以審核者確認照片
階段 3（依賴核實計畫 P4 指標）
  └─ 各等級採納率、駁回率、審核者確認量；校準 N、P 與限流
```

每階段獨立 PR，附 migration、pgTAP、Flutter 測試與回退方案。階段 2 之前，#85 §5.2 的照片內容確認仍只能由管理員執行。

## 8. 待拍板決策

1. **是否採用「信任等級」方向**（§4 選項 B），並確認不做遊戲化。
2. **等級是否公開。** 建議：一般等級不公開；審核者／管理員在「資料與查核」區可標示角色。
3. **審核者是否要求 MFA（`aal2`）。** 建議要求。
4. **T2 門檻**：N 則採納、P% 採納率的初值。建議從 N=10、P=80% 起，上線後依 P4 指標調整。
5. **等級是否影響每日限流。** 建議 T2 從每帳號 10 筆提高到 20 筆，仍低於每 IP 30 筆的上限，避免一名 T2 車友耗盡同一行動網路 NAT 下其他車友的額度；IP 上限不變；T0／T1 維持。
6. **駁回分類**是否納入階段 0 立即實作。
7. **審核者的欄位白名單**：建議名稱、入口說明、停車指引；費率與車種欄位排除。`note`（備註）是自由文字，可能夾帶「重機可停」之類的資格宣稱，是否納入白名單需決定；若納入，審核者採納時應確認內容不含資格宣稱。
8. **審核者是否以 T2 為硬條件。** 建議冷啟動期為建議條件、由管理員裁量，等 P4 指標顯示 T2 人數足夠後再改為硬條件。
9. **撤銷審核者後，其已確認的核實如何處置。** 建議預設回到 `disputed` 送管理員複查；若撤銷原因與審核品質無關（例如本人請辭），可保留。
10. **是否修訂 `docs/ADMIN_WEB.md`。** 審核者角色與「不在範圍內：多層級角色」衝突，P7 使用者頁也需納入等級檢視與授予／撤銷；採用本方案時應同步修訂。

## 9. 必測情境（實作時納入）

| 情境 | 預期 |
| --- | --- |
| 帳齡 6 天的帳號送出觀察 | 記錄為觀察，`qualified=false`，不計入存在核實與 #85 §5.2 例外 |
| T2 車友與 T1 車友各一筆觀察 | 兩筆權重相同，皆為 1 |
| 使用者修改自己的 `raw_user_meta_data` 加入 `tier` 或 `role` | 等級與角色判定不受影響 |
| 審核者嘗試採納 `heavy_allowed` 建議 | `42501` 拒絕；稽核不留採納紀錄 |
| 審核者確認照片後社群門檻達成，但該欄位有有效期內的管理員核驗 | 不覆蓋，標 `disputed` |
| 審核者確認自己送出的案件的照片 | 拒絕 |
| 管理員撤銷審核者 | 該審核者 JWT 刷新後 `is_reviewer()` 為 false；其已確認的核實依 §8 第 9 點回到 `disputed` 或保留 |
| 一則建議被以 `abuse` 駁回 | 回報者 180 天內降為 T0；`wrong` 駁回不影響 T1 |
| 非本人呼叫 `my_contributions()` 或直接讀 `contributor_standing` | 只回本人資料；RLS 拒絕讀他人 |
| 公開 view 與 viewport RPC | 不含任何等級、計數欄位 |
