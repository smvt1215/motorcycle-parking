# 貢獻等級與遊戲化機制 — 可行性研究

> 狀態：研究結論與設計提案，尚未實作  
> 日期：2026-10-25（Asia/Taipei）  
> 盤點基準：`main` commit `40d96db`（含 #76）；另參考審核中的 #81、#83、#84、#85  
> 依據：[社群共筆與停車資訊核實機制](COMMUNITY_VERIFICATION_PLAN.md)（以下稱「核實計畫」）、[Admin Web 計畫](ADMIN_WEB.md)、[專案總計畫「社群回報機制」](PLAN.md#社群回報機制)  
> 目標（2026-10-25 使用者決定）：**加入遊戲化機制，使 95% 的審查由社群完成**，管理員只處理剩下的 5%。  
> 性質：本文不更改程式。採用本方案時，核實計畫 §1「不在本計畫範圍」中的「公開使用者排行榜、可交換點數等遊戲化機制」一句需另開 PR 修訂（#85 正在修改同一份文件，本 PR 不動它）。

## 1. 結論

**95% 社群審查是可以達成的目標，但前提是三件事同時成立：社群要能「結案」而不只是「提供觀察」、遊戲化只獎勵「事後證明正確」的貢獻、管理員的 5% 要定義成「爭議、申訴、法規與隨機抽查」而不是「剩下沒人審的」。**

- **今天 0% 由社群結案。** `moderation_queue` 只能由 `admin_resolve_report`（`is_admin()`）結案；社群只能送出觀察與舊 `vote`。要到 95%，核心不是獎勵，而是先給社群一條能結案的路徑：審核任務、共識規則、依風險分級決定誰能結案（§5）。
- **遊戲化可以納入，但要綁在結果上。** 點數只在「採納、共識成立、照片被確認」時發放，在「被翻案」時扣回並加罰；等級同時看點數與準確率，刷量不會升級（§5.3、§5.4）。這與核實計畫原則 2「社群提供觀察與證據，不以多數票取代法規」並不衝突：法規與路邊格位合法性仍是管理員禁區，社群結案的是事實類欄位與路外場站業者規則（#85 §5.2 例外）。
- **信任等級是遊戲化的骨架。** 系統已有沒有名字的兩層（帳齡 7 天決定 `qualified` 與權重 0.25／1）與管理員布林角色（§3）。本文擴成 L0–L4 五級加管理員，L3 以上自動取得 #85 要求的「經授權的審核角色」能力（照片內容確認），不再只靠管理員人工授予（§5.2）。
- **95% 要用指標驗收，不是宣告。** §2 定義「社群結案率」與護欄指標「翻案率」；每個欄位類別只有在翻案率低於門檻時才開放社群自動結案，否則退回管理員。管理員的 5% 中固定包含隨機抽查，這是量測翻案率的來源。
- **誠實的限制。** 95% 是吞吐量目標，取決於活躍審核者人數。冷啟動期達不到，建議分段 50% → 80% → 95%（§9）。每月約需「案件數 × 3」次審核動作，少於這個量就會回落到管理員（§2.3）。
- **仍然不建議的部分。** 可兌換金錢或實物的點數：涉及稅務、消費者保護與更強的刷分誘因，建議第一年只做非金錢的等級、徽章、排行榜與任務；是否開放兌換列為 §10 決策。

## 2. 目標定義與量測

### 2.1 指標

| 指標 | 定義 | 目標 |
| --- | --- | --- |
| **社群結案率** | 當月結案的審核案件中，由社群機制（共識自動結案、L3／L4 結案）結案的比例。分母排除「政策規定只能由管理員處理」的類別（§5.1 禁區）與管理員隨機抽查本身 | 分段：上線 3 個月 ≥ 50%、6 個月 ≥ 80%、12 個月 ≥ 95% |
| **管理員占比** | 當月管理員親自結案的案件（含禁區與抽查）占全部結案的比例 | 穩態 ≤ 5%＋禁區案件；禁區案件另列 |
| **翻案率**（護欄） | 社群結案後 90 天內被管理員或後續證據推翻的比例，依欄位類別分開算 | 低風險 ≤ 3%、中風險 ≤ 5%；超過即該類別暫停自動結案 |
| **抽查不合格率**（護欄） | 管理員隨機抽查社群結案案件的不合格比例 | 與翻案率同門檻；抽查比例起始 5%，翻案率穩定後可降到 2% |
| 審核時效 | 案件從送出到結案的中位數天數 | 社群 ≤ 7 天（參考值，依資料調整） |
| 審核者覆蓋 | 近 30 天完成至少 1 件審核任務的 L1＋人數、每縣市分布 | 監看用，決定是否有足夠人力開放某縣市 |

### 2.2 為什麼分母要排除禁區

縣市法規、路邊格位合法性、官方點欄位的來源、申訴終審，核實計畫 §1 原則 2 與 §3.3 要求只能由官方資料或管理員判定。這些案件無論社群多活躍都不能由社群結案；把它們放進分母，95% 會變成做不到的數字，反而誘使放寬禁區。正確做法是**讓禁區案件量本身很小**：法規由管理員維護 `city_rules` 而非逐案審；官方點只接受修改建議、不開放隱藏；申訴只在翻案時發生。

### 2.3 人力試算

每件案件依 §5.1 需要 2–3 名獨立審核者；加上 5% 抽查與爭議，粗估每件 3 次審核動作。

```text
每月所需審核動作 ≈ 當月案件數 × 3
每月所需活躍審核者 ≈ 審核動作 ÷ 每人每月願意做的件數（保守 5 件）
例：每月 200 件 → 600 次審核 → 約 120 名活躍 L1＋，且要分布在案件所在縣市
```

活躍審核者少於這個量時，案件會逾時（§5.1 的 14 天）回到管理員，社群結案率自然下降。這就是為什麼遊戲化要存在：它的工作是把「願意做 5 件」的人數養起來，而不是讓每個人做更多件。

### 3.2 現在缺的

- **社群沒有結案路徑。** 只有 `admin_resolve_report` 能把案件從 `pending` 改掉。
- **使用者看不到自己的貢獻。** `moderation_queue` 只有 `admin_read_moderation` 一條讀取政策；貢獻頁（`lib/features/contribute/`）只列目前地圖範圍內的停車點。
- **駁回沒有分類。** `rejected` 只有自由文字 `resolution_note`，分不出「判斷錯誤」「重複」「濫用」。
- **沒有使用者資料表。** #83 把顯示名稱與頭像放在 `raw_user_meta_data`（使用者可自改）；#81 把名稱快照到 `community_spots.contributor_name`。等級、點數屬伺服器判定的資料，**不能放 `raw_user_meta_data`**。
- **沒有中間角色。** `is_admin()` 是布林；#84 的核驗 trigger 與所有管理 RPC 都以它為唯一閘門。
- **沒有照片上傳。** 核實計畫 P2 的 `spot_evidence` 尚未實作；#85 §5.2 例外與本文 L3 的照片確認都依賴它。

## 5. 達到 95% 需要的機制

### 5.1 社群審核流程與共識規則

**審核任務。** 每件待審案件（修改建議、新增停車點、已不存在回報、照片證據）成為一個任務，推給符合條件的審核者：不是提案者本人、與提案者不同 IP／裝置、等級達到該風險類別的門檻、近期在該縣市有活動（以目前地圖範圍查詢，不儲存位置歷史）。任務內容是「目前值／建議值／證據」加上三個選項：同意、不同意、無法判斷，並可附現場照片。

**依風險分級決定誰能結案。** 每票權重都是 1；等級決定「能不能投」與「結案需要哪種組合」。

| 風險 | 欄位／案件 | 結案條件（自動） | 失敗時 |
| --- | --- | --- | --- |
| 低 | 名稱、入口說明、停車指引、備註、照片是否可公開 | 2 票同意（L1＋）、0 票不同意、提案 `base_revision` 未變 | 任一不同意 → 升為中風險處理 |
| 中 | 費率、格位型式、場站型式、位置移動 ≤ 150 m、點位存在、社群點「已不存在」 | 3 票同意、其中至少 1 名 L2＋、0 票不同意；「已不存在」先降為待確認，再 3 票才隱藏 | 任一不同意 → 標 `disputed`，由 L4 初審；L4 無法定案 → 管理員 |
| 高 | 路外場站業者的車種規則（#85 §5.2 例外） | 3 名獨立 L1＋同意＋1 張經 L3 確認內容的入口公告照片；型式與位置已由官方或管理員核實；無相反觀察；寫入 `source_kind='community'`，有效期 90 天 | 相反觀察 → `disputed` → 管理員 |
| 禁區 | 縣市法規、路邊格位合法性、官方點欄位與來源、官方點隱藏、申訴終審、撤銷角色 | 只有管理員 | — |

- 等級高不會讓一票變兩票；L3 在高風險類別的角色是「確認照片」，不是「多一票」。
- 任務 14 天無人完成或票數不足 → 回到管理員佇列，並計入「社群未結案」。
- 同一欄位出現矛盾的可靠觀察時，保留前一個安全狀態、標 `disputed`，不採最新覆蓋（核實計畫 §5.2）。
- 自動結案以單一 transaction 執行：比對版本 → 寫欄位 → 寫 `spot_field_verifications` → 結案 → 寫稽核（actor 記為系統，附參與審核者 ID），與 `admin_resolve_report` 同一套衝突檢查（`40001`）。

### 5.2 信任等級

| 等級 | 取得（自動，除 L4 另註） | 審核能力 | 其他 |
| --- | --- | --- | --- |
| L0 新車友 | 登入，帳齡 < 7 天或未完成新手任務 | 可做任務但**不計票**（訓練模式，只做黃金任務，見 §5.4） | 回報權重 0.25（現行）；每日 10 筆 |
| L1 車友 | 帳齡 ≥ 7 天、新手任務 ≥ 5 件且黃金任務準確率 ≥ 80%、近 180 天無濫用 | 低風險計票；高風險的「3 名獨立車友」計數 | 回報權重 1 |
| L2 熟手 | 點數 ≥ 100、審核任務 ≥ 20 件、準確率 ≥ 85% | 中風險計票 | 可標 `disputed`；每日 20 筆 |
| L3 核實者 | 點數 ≥ 500、任務 ≥ 100 件、準確率 ≥ 90%、近 365 天無翻案罰分達上限 | 照片內容確認（#85 §5.2）；低風險可單獨結案（1 票 L3＋1 票 L1） | 縣市排行榜顯示（選擇加入）；每日 30 筆 |
| L4 守護者 | L3 滿 90 天且準確率 ≥ 95%，再由管理員確認；或管理員直接授予 | `disputed` 初審、L0–L2 的申訴初審、抽查協助 | 需 `aal2`；可被管理員撤銷 |
| A 管理員 | 既有 `is_admin()` | 禁區案件、申訴終審、隨機抽查、撤銷角色、調整門檻 | — |

- 準確率＝「與最終結果一致的審核票」÷「已有最終結果的審核票」，黃金任務計入。
- 降級自動：準確率跌破門檻或翻案罰分累積即降一級；濫用（管理員標記）直接回 L0 並凍結 180 天。
- L3、L4 存 `app_metadata.role`（`verifier`／`guardian`），由 service role 依 standing 表寫入；JWT 內就能判斷，與 `is_admin()` 同機制。

### 5.3 遊戲化：點數、等級、徽章、排行榜、任務

**點數只獎勵事後證明正確的行為，並且可以扣回。**

| 行為 | 點數 | 說明 |
| --- | --- | --- |
| 修改建議被採納 | ＋10 | 採納時發放 |
| 新增停車點通過存在核實 | ＋20 | 兩名獨立 L1＋確認後發放 |
| 照片證據被 L3 確認且用於核實 | ＋5 | 照片通過隱私處理後才計 |
| 審核票與最終結果一致 | ＋3 | 結案時發放；「無法判斷」不加不扣 |
| 黃金任務答對 | ＋1 | 不公開哪些是黃金任務 |
| 自己的貢獻在 90 天內被翻案 | －15 | 扣回原點數再罰 5 |
| 審核票與管理員終審相反 | －3 | 只在 `disputed` 經管理員裁決時 |
| 黃金任務答錯 | －5 | 並降低準確率 |
| 被標記濫用 | 清零 | 回 L0 並凍結 |

限制：每人每日點數上限（建議 60）；同一停車點每人每 90 天最多計一次審核點數；同一提案者的建議不會連續三次派給同一審核者。

**等級**就是 §5.2，顯示為名稱與徽章，不顯示原始點數給他人。

**徽章**（非排名、可累積）：縣市首筆核實、連續 4 週有審核、100 件任務零翻案、照片證據 20 張被採納、協助結案一件 `disputed`。徽章不給點數，只給辨識。

**排行榜**：每月、每縣市，只列選擇加入的 L2＋，顯示 `display_name`（#83）與等級，不顯示貢獻的地點；每月重置，另有「本月最準確」榜（準確率，需 ≥ 20 件）與「本月最多」榜並列，避免只獎勵量。

**任務**：「本週你所在縣市有 N 件待審」「這個停車點需要第 3 位確認」；新手任務引導完成 5 件黃金任務。推播沿用既有 `lib/core/notifications.dart`，頻率上限每日 1 則。

**不做的事**：不做每日簽到、不做連續登入獎勵（製造無意義操作）、不把點數換成金錢或實物（§10 決策 5）、不在地圖標記或資格橫幅上顯示任何等級或點數。

### 5.4 防刷與品質控制

| 手段 | 做法 |
| --- | --- |
| 黃金任務 | 管理員已確認答案的案件混入任務流（約 10%），用來量準確率與擋機器式點擊；答案不公開，定期更換 |
| 結果綁定 | 點數在結案時發放、翻案時扣回；刷量沒有結果就沒有點數 |
| 獨立性 | 沿用 `apply_report` 的同 IP／裝置檢查與帳齡；同 IP 的多票只算 1 票，不把 IP 當身分（核實計畫 §5.2） |
| 共謀偵測 | 兩個帳號在 30 天內共同出現於 ≥ 10 件任務且投票一致率 ≥ 95% → 列入風險旗標，點數暫緩發放，由管理員檢視 |
| 位置合理性 | 任務只派給「目前地圖範圍在該縣市」的使用者；不要求也不儲存精確位置 |
| 冷卻與上限 | 每日任務上限（L1 10、L2 20、L3 30）、每日點數上限、同點位 90 天一次 |
| 抽查 | 管理員每月隨機抽查社群結案的 5%（穩定後 2%）；不合格即翻案並扣分 |
| 翻案率閘門 | 依欄位類別統計；超過門檻的類別自動關閉共識結案，退回管理員，直到連續兩個月低於門檻 |
| 申訴 | 被扣分者可申訴一次；L4 初審、管理員終審 |

### 5.5 管理員的 5% 是什麼

1. 禁區案件（§5.1）。
2. `disputed` 經 L4 初審仍無法定案者。
3. 申訴終審。
4. 隨機抽查（這是翻案率與抽查不合格率的資料來源，不是可省略的工作）。
5. 調整門檻、黃金任務、撤銷角色、處理共謀旗標。

管理員不再逐案審核事實類欄位。若抽查顯示某類別品質不足，關閉該類別的社群結案，讓它暫時回到管理員，這是設計內的退路，不是失敗。

## 6. 資料模型與 API（建議，實作時再定版號）

**新增表**

- `review_tasks`：`id`、`case_id → moderation_queue.id`、`risk text`（`low/medium/high`）、`field_key`、`required_votes`、`min_level`、`expires_at`、`status`（`open/resolved/escalated/expired`）、`is_gold boolean`（不公開）、`gold_answer jsonb`（只有 service role 可讀）。
- `review_votes`：`task_id`、`reviewer_id`、`vote`（`agree/disagree/unsure`）、`evidence_ids`、`ip_hash`、`device_hash`、`created_at`；唯一鍵 `(task_id, reviewer_id)`；RLS：本人讀自己的票，管理員全部，公開 view 不含。
- `contributor_standing`：`user_id PK`、`level`、`points`、`accuracy numeric`、`votes_total`、`votes_scored`、`accepted_count`、`reversed_count`、`abuse_count`、`frozen_until`、`leaderboard_opt_in boolean`、`computed_at`。
- `point_ledger`（append-only）：`user_id`、`delta`、`reason`、`ref_table`、`ref_id`、`created_at`；扣回以負數列表示，不改歷史。
- `badges`、`user_badges`。
- `audit_samples`：管理員抽查的案件、結果、抽查者。
- 沿用核實計畫 P2 的 `spot_observations`、`spot_evidence`、P3 的 `spot_field_verifications`。

**既有表調整**

- `moderation_queue`：加 `risk`、`resolved_by_kind`（`admin/community/guardian/system_expired`）、`resolution_kind`（`wrong/duplicate/abuse/other`，駁回必填）；`resolved_by` 社群結案時為 null，參與者記在 `review_votes` 與稽核。
- `admin_audit_log`：新增 `action` 值 `community_resolve`、`audit_sample`、`set_role`、`reverse_decision`。

**新 RPC**

- `next_review_tasks(p_city, p_limit)`：依等級、獨立性、縣市派任務；黃金任務混入。
- `submit_review_vote(p_task, p_vote, p_evidence)`：經 `submit-report` Edge Function 進入（沿用 IP／裝置雜湊、限流）；投票後檢查共識並在同一 transaction 結案、發點數、寫核實與稽核。
- `my_contributions()`：本人的建議、狀態、等級、點數、徽章、距下一級差距。
- `leaderboard(p_city, p_month)`：只回選擇加入者的 `display_name`、等級、名次；security definer 內部過濾。
- `confirm_evidence(p_evidence, p_supports, p_note)`：L3＋；寫 `spot_evidence.content_confirmed_by/at` 與稽核。
- `guardian_resolve_dispute(p_case, p_decision, p_note)`：L4；只能在 `disputed` 案件上做「維持前一安全狀態」或「送管理員」，不能直接採納高風險值。
- `admin_reverse_decision(p_case, p_note)`：翻案；扣點、更新準確率、寫 `audit_samples`。
- `admin_set_role(p_user, p_role, p_note)`、`admin_set_category_gate(p_risk_or_field, p_enabled)`。
- 每日 job：重算 `contributor_standing`、處理到期任務、更新翻案率與閘門、同步 `app_metadata.role`。

**與 #84 的關係**：社群結案不呼叫管理員 RPC，`community_spots_vehicle_verification` 不會記錄管理員核驗；高風險類別的社群核實寫入 `spot_field_verifications`（`source_kind='community'`），不覆蓋有效期內的 `admin`／`official` 列（#85「不覆蓋較高來源」）。

## 7. 使用者介面

- **App「貢獻」頁**改為三區：我的等級與點數（含距下一級差距）、待我審核的任務（依目前地圖縣市）、我送出的建議與狀態。
- **審核任務頁**：目前值／建議值／證據並排，三個按鈕，附照片入口；L0 看到「訓練模式，答案不計票」。
- **詳情頁**沿用 #81「由車友 XXX 回報」，另在「資料與查核」區顯示「由 N 位車友確認・YYYY-MM-DD」；資格橫幅依 #85 §3.4 分層，不顯示等級。
- **排行榜**在貢獻頁內，預設顯示本縣市本月；首次進入詢問是否加入顯示。
- **Admin Web**：審核佇列加「社群結案」「抽查」「爭議」「禁區」四個分頁；使用者頁（P7）加等級、點數、準確率、角色授予／撤銷、凍結；指標頁顯示 §2.1 全部指標與各類別閘門狀態。

## 8. 風險

| 風險 | 說明 | 緩解 |
| --- | --- | --- |
| 95% 達不到 | 活躍審核者不足，任務逾時回到管理員 | 分段目標；指標頁顯示每縣市覆蓋；逾時案件由管理員處理但計入「未達」，不美化 |
| 刷分 | 為點數亂投同意 | 點數綁結果、黃金任務、翻案扣分、每日上限、準確率門檻 |
| 共謀 | 多帳號互相確認 | 獨立性檢查、共謀偵測、L2 以上才能計中風險票、抽查 |
| 把事實共識誤當合法 | 社群結案的「可停」被當成合法保證 | 禁區不變；資格橫幅只依 #85 §3.4；社群核實與官方分開標示 |
| 資深者霸凌 | L3／L4 壓制新手 | 每票權重 1；L4 只能維持安全狀態或送管理員，不能定案；申訴機制 |
| 排行榜負面效應 | 只衝量、互相攻擊 | 選擇加入、每月重置、準確率榜並列、不顯示地點 |
| 隱私 | 點數、任務暴露活動地區 | 任務只用目前縣市、不存位置；排行榜只顯示縣市與名稱；standing 只本人與管理員可讀 |
| 法律 | 點數若可兌換涉稅務與消保 | 第一年不開放兌換；開放前法務確認 |
| 維運 | 多套狀態機、每日 job、黃金任務維護 | 分階段；每階段 pgTAP 與 Flutter 測試；閘門可一鍵關閉某類別 |
| 核實計畫文件不一致 | §1 不在範圍句與本方案衝突 | #85 合併後另開 PR 修訂 §1、§2.2、§11，並把本文列為附屬設計 |

## 9. 分階段與依賴（每階段以指標驗收）

```text
階段 0（可立即，與核實計畫 P1 並行；不改權重，不發點數）
  ├─ moderation_queue.resolution_kind、risk；Admin Web 駁回必選
  ├─ my_contributions() + 貢獻頁「我的建議」
  ├─ 量測基線：每月案件數、管理員結案時效、回報者人數（LEAN UX 待驗證項）
  └─ 另開 PR 修訂核實計畫 §1 不在範圍句（待 #85 合併）
階段 1（依賴核實計畫 P2：spot_observations、spot_evidence）
  ├─ review_tasks／review_votes／contributor_standing／point_ledger
  ├─ 低風險類別共識結案（2 票）＋ 黃金任務 ＋ 點數
  ├─ L0–L2 自動等級；排行榜（選擇加入）
  └─ 驗收：低風險翻案率 ≤ 3%、社群結案率 ≥ 50%
階段 2（依賴核實計畫 P3：spot_field_verifications）
  ├─ 中風險共識結案（3 票含 L2＋）；disputed 流程
  ├─ L3 照片內容確認 → #85 §5.2 例外由社群完成
  ├─ L4 守護者、申訴、管理員抽查佇列、翻案 RPC
  └─ 驗收：中風險翻案率 ≤ 5%、社群結案率 ≥ 80%
階段 3（依賴核實計畫 P4 指標）
  ├─ 指標頁、類別閘門自動化、共謀偵測
  ├─ 徽章、任務推播
  └─ 驗收：社群結案率 ≥ 95%、管理員占比 ≤ 5%＋禁區
```

每階段獨立 PR，附 migration、pgTAP、Flutter 測試、功能旗標與回退方案；任何類別的社群結案在端到端驗收前不開啟（核實計畫 §10）。

## 10. 待拍板決策

1. **確認方向**：採用「結果綁定的遊戲化＋分級共識結案」，並修訂核實計畫 §1 的不在範圍句。
2. **指標分母**：社群結案率是否如 §2.2 排除禁區案件（建議排除，另列禁區量）。
3. **分段目標與時程**：50%／80%／95% 的月份數。
4. **每票權重**：維持全部為 1（建議），或允許 L3 在中風險類別算 2 票（不建議，會重建多數決問題）。
5. **點數兌換**：第一年只做非金錢（建議）；若要兌換，先法務確認。
6. **排行榜範圍**：每月每縣市、選擇加入（建議）；是否要全國榜。
7. **黃金任務來源與比例**：管理員標記已確認案件，約 10%；誰負責維護題庫。
8. **L4 的產生方式**：L3 滿 90 天＋管理員確認（建議），或純管理員授予。
9. **抽查比例**：起始 5%，穩定後 2%。
10. **點數表數值**（§5.3）與每日上限 60 的初值。
11. **`note` 備註**是否列為低風險：自由文字可能夾帶資格宣稱；建議列低風險但審核任務提示「不得含可停／不可停」。
12. **是否修訂 `ADMIN_WEB.md`**：多層級角色、P7 範圍、指標頁。

## 11. 必測情境（實作時納入）

| 情境 | 預期 |
| --- | --- |
| 帳齡 6 天的帳號投審核票 | 記錄為訓練票，不計入共識，不發點數 |
| 2 名 L1 對低風險建議投同意 | 自動採納、寫核實、發點數、寫稽核（actor 為系統，附兩人 ID） |
| 2 名同 IP 不同帳號投同意 | 只算 1 票，任務維持 open |
| 提案者自己投票 | 拒絕 |
| 3 名 L1 對費率建議投同意、無 L2＋ | 不結案，等待 L2＋ |
| 中風險任務出現 1 票不同意 | 標 `disputed`，進 L4 佇列，不採納 |
| 高風險：3 票同意但照片未經 L3 確認 | 不核實 |
| 高風險：社群門檻達成，但該欄位有有效期內管理員核驗且值相反 | 不覆蓋，`disputed` |
| 路邊格位的車種建議 | 不產生社群任務，直接進管理員禁區 |
| 共識結案前點位 `updated_at` 已變 | `40001`，任務重置 |
| 管理員翻案 | 參與者各扣分、準確率更新、`audit_samples` 留紀錄 |
| 某類別翻案率連續超門檻 | 該類別新任務改派管理員；既有任務到期回管理員 |
| 黃金任務答錯 | －5、準確率下降；答案不外流到任何 API |
| L3 準確率跌破 90% | 自動降 L2，`app_metadata.role` 移除，JWT 刷新後 `confirm_evidence` 拒絕 |
| 使用者修改 `raw_user_meta_data` 加入 `level`／`points`／`role` | 判定不受影響 |
| 未選擇加入者 | 不出現在 `leaderboard()`；他人讀不到其 standing |
| 公開 view 與 viewport RPC | 不含等級、點數、票數欄位 |
| 每日點數達上限 | 之後的正確票仍計準確率，不計點數 |
