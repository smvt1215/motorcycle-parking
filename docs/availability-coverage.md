閾值依實測更新節奏定：臺北市停管處約每 5 分鐘產生一次（3 輪抽樣時檔頭距今 6.6、4.8、2.0 分鐘），新鮮設為兩個週期；臺南 Parkweb 逐筆時間中位數 4.1–5.7 分鐘；新竹 hispark 逐筆時間全在 2.7 分鐘內。這些門檻只根據一個下午的樣本，上線後以 `parking_availability_history`（若啟用）的實際分布再校正。

臺北的新鮮時窗自 migration `202610310500` 起改為相對「預計下一批」：檔案在 `UPDATETIME` 後約 70 秒才公開（staging 實測 `Last-Modified`），舊的固定排程（整 5 分＋1 分）因此每次讀到上一批，資料年齡在 6–11 分鐘間跳動、在 10 分鐘線上新鮮／延遲來回切換。現在依 `UPDATETIME`＋5 分＋學到的公開延遲推算擷取時間，新鮮時窗為 5 分＋公開延遲＋4 分寬限（一個排程間隔、一次 App 輪詢與 1 分餘裕），`viewport_availability.fresh_seconds` 回傳同一個值。

所有來源共同的規則（落實計畫 §2、§5.1）：

1. `-1`（TDX）、`-9`（臺北、新北）→ 無即時資料，不是 0。其他負值（新北出現 `-4`、`-6`，官方說明未列）→ `invalid`。
2. 剩餘數大於該車種容量 → `invalid`（臺中 TDX 有 5–6 場、新竹 2 場；見 §5）。
3. 該車種容量為 0 或缺欄位 → 不顯示該車種膠囊，避免把「沒有機車格」寫成「已滿」。重機膠囊只在該場站有有效重機值時顯示；無值時不顯示，也不顯示 0。
4. 同一場站連續 N 輪（建議 ≥ 2 小時）剩餘數都是 0 且來源有機車容量 → 標 `invalid` 並列入稽核，不顯示「已滿」。抽樣中這類場站比例不低（§5.4），在確認是真滿還是佔位值前不能直接顯示。
5. 新鮮度只看來源時間（臺北檔頭 `UPDATETIME`、臺南與新竹逐筆時間），不看抓取時間；TDX 的 `DataCollectTime` 在臺南、高雄已確認是轉發時間（§5.3），不能當來源時間。
6. 停車場暫停營運沒有可靠的即時欄位（§5.5），第一批不顯示「暫停」，維持靜態資訊；營運異常改走既有修改建議流程。

## 5. 特殊值與資料異常

### 5.1 無資料代碼

- TDX：`AvailableSpaces = -1`「未知/以現場為主(含非營業時段)」。抽樣中 TDX 路外只在高雄出現 1 筆機車 `-1`；臺北 TDX 多半直接不列沒有資料的車種（`Availabilities` 陣列沒有 `2`），所以「缺車種欄位」與 `-1` 都要視為無資料。
- 臺北停管處：`-9`。1,223 場中 1,007 場機車為 `-9`，有機車容量的 314 場中 98 場為 `-9`；重機 98 場中 75 場為 `-9`。
- 新北市：官方說明「部分停車場因更換營運廠商，尚無提供即時車位，其顯示數值將為-9」；實測另有 `-4`、`-6`（說明未列），依計畫列為 `invalid`。

### 5.2 佔位值（新北 TDX 路邊）

新北 TDX 路段剩餘的每個車種 `AvailableSpaces` 全部是 0，但路段總剩餘為正數（例：ID N34 總剩 7，汽車 0、身障 0）；3 輪中 795 個有機車容量的路段機車值都是 0，從未變動。這些 0 是佔位，不是「已滿」。工具以「各車種皆為 0 但總剩餘 > 0」判定為佔位；臺北 TDX 的總剩餘只算汽車，與車種加總不同屬正常，不判定為佔位。

## 9. 使用者決定（2026-10-26）

1. **第一批即時車位只上臺北**：資料來源是臺北市停管處 `TCMSV_allavailable.xml`（V2）。臺南 Parkweb、新竹 hispark 之後再加；其他縣市只顯示靜態容量。
2. **臺中、高雄先延長抽樣**：連續抽樣 3 天，含夜間與假日，再決定是否付費接 TDX（基礎會員每月 3 點不足以輪詢，見 §3）。追蹤於 issue #126。
3. **重機剩餘數膠囊第一批就上**：只在有有效重機值的場站顯示（臺北抽樣時 23 場）；`-9`、缺欄位或重機容量為 0 時不顯示，也不顯示 0。
4. **重機停汽車格（A，併入第一批）**：依法大型重機可停汽車格。臺北路外場站在資料已確認重機可停汽車格時（場站或分區明確開放重機使用汽車格），另外顯示汽車格剩餘膠囊（汽車圖示＋「剩 N」，詳情為「汽車格剩餘 N」，#129）：
   - 來源是停管處 XML V2 的 `AVAILABLECAR`，新鮮度規則與機車相同；`-9` 算無資料，剩餘大於汽車容量（`TCMSV_alldesc.json` 的 `totalcar`）算異常。
   - 與重機專用剩餘數分開、用中性色，不能算成重機有位；費率照汽車。沒確認的場站不顯示。
   - 路邊汽車格（重機可停）圖層另外設計，見 issue #127，本稽核不涵蓋。
5. **路邊路段 P2 只做靜態路段**：抽樣的 8 個縣市都缺少機車路段即時資料（臺北「含機車」路段是汽機車共用格、新北分車種值是佔位 0、其他縣市只有汽車，見 §4.3），路邊維持「共 N 格／空位未知」。

### 9.1 重機停汽車格：staging 臺北符合條件的點

| 條件 | 點數 |
|---|---|
| staging 臺北官方點 | 509 |

目前沒有任何臺北點位能顯示這個膠囊，缺的是**逐場站的確認資料**，不是即時資料：

## 10. 重跑方式

```bash
# 原始回應放在版控以外的目錄；TDX 憑證從環境變數或 supabase/functions/.env 讀取，不會寫入輸出。
python3 tool/availability_audit.py fetch --out <scratch>/r1
python3 tool/availability_audit.py fetch --out <scratch>/r2 --kinds OffStreet/ParkingAvailability,OnStreet/ParkingSegmentAvailability
python3 tool/availability_audit.py analyze <scratch>/r1 <scratch>/r2 --staging <staging 官方點 JSON> > summary.json
```

下列數字不是 `analyze` 的輸出，是 2026-10-26 以同一批原始回應手動查詢得到；重跑時照此方法操作：

- **TDX `Alert`（§5.5）**：`fetch --kinds Alert --cities Taipei,Kaohsiung,Taichung --city-sources none` 取得原始回應，依 `Title`、`Status`、`Effect` 計數；把 `CarParks[].CarParkID` 與同時段 `OffStreet/ParkingAvailability` 的 `CarParkID` 取交集，再看交集內的 `ServiceStatus`。
- **臺中名稱對應（§6）**：staging `TXG` + 市府 `ID` → 市府資料集同 `ID` 的 `Position` → 與 TDX `ParkingAvailability` 的 `CarParkName.Zh_tw` 完全相同且唯一者算對上；再檢查機車項 `NumberOfSpaces > 0` 且 `0 ≤ AvailableSpaces ≤ NumberOfSpaces`。
- **重機停汽車格（§9.1）**：staging 以唯讀 SQL 取臺北未隱藏官方點的 `source_id`、`parking_access`、`parking_zones[].access`；與同一輪 XML 的 `AVAILABLECAR`、`TCMSV_alldesc.json` 的 `totalcar` 依 `source_id` = `ID` 對照。
- **交叉比對（§8）**：臺北以 `CarParkID` = 停管處 `ID` 對照同一輪的 TDX 與 XML；臺南以名稱前 4 字對照 TDX 與 Parkweb；臺中以名稱完全相同對照 TDX 與市府燈號；高雄以去掉「停車場」後的名稱對照 TDX `ParkingSpace` 與市府一覽表；桃園以名稱完全相同對照 TDX 與市府 XML。

`fetch` 會以 13 秒間隔呼叫 TDX（每把金鑰每分鐘 5 次），遇 429 依 `Retry-After`（秒數或 HTTP 日期，無法解析時等 60 秒）等待；某個縣市來源回非 JSON 時記錄錯誤並繼續下一個來源；縣市來源優先使用 IPv4（新北主機的 IPv6 位址無回應）。staging 官方點以唯讀方式取得 `id, source_id, city`。
